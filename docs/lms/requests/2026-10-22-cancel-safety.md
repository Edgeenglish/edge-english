# 수업 취소·변경·보강 안전장치 요청 (2026-10-22 대표, 실제 사고 후)

> 대표 지시: "하던 작업 마치고, 맞는 순서에 끼워 줘." 첫 작업은 **기존 설계·코드 검토 후 세 가지로 구분 보고**(구현 아님). H23 개발 순서·운영 DB 작업은 그대로. 운영 DB·학생 데이터·대외 발송은 별도 승인 없이 바꾸지 않음. 정책 원본 H24에 요약 기록.

## 1. 사고
학생이 일요일에 카톡으로 "다음 주 목요일 수업이 어렵다" → 운영진이 **다다음 주 목요일** 수업을 취소. 학생에게 **보강 날짜만** 알리고 **원래 취소되는 날짜는 안내하지 않음** → 학생·강사가 서로 다른 일정을 인지, 강사가 수업 시간에 학생을 기다림.

## 2. 학생이 LMS에서 직접 취소
- 예정 수업 목록 → 그 수업의 [취소] → 취소 직전에 실제 날짜·시간을 크게: "10월 29일(목) 오후 5시 수업을 취소하는 것이 맞나요?" [돌아가기] [취소 확정]
- 카톡보다 편해야 함: 모바일 최소 단계, 사유 입력 강제 안 함, 로그인한 학생에게 재인증 요구 안 함
- 변경권·6시간 규정·보강 가능 여부는 기존 정책으로 자동 검사, 취소 후 처리 결과·남은 변경권·보강 가능 여부 표시

## 3. 카톡 요청을 운영진이 대신 입력
1. 카톡에서 요청 확인 → 2. 관리자 LMS에서 학생 검색 → 3. 실제 예정 수업 목록 → 4. 원래 수업 날짜·회차를 **직접 선택** → 5. 취소 규정·변경권 자동 확인 → 6. 처리 확정 → 7. 정확한 수업 날짜가 들어간 안내문 생성 → 8. 카톡 발송 및 발송 상태 기록
- 학생 직접 신청과 운영진 대신 처리는 **같은 수업 데이터·같은 정책 검증**
- 학생에게 되물으면 답이 없는 경우가 많음 → 요청이 충분히 명확하면 추가 회신 없이 처리하고, 안내문에 날짜를 명시: "요청하신 10월 29일(목) 오후 5시 수업이 취소 처리되었습니다. 요청하신 날짜와 다르다면 바로 말씀해 주세요."
- 날짜가 모호하거나 두 수업 이상으로 해석되면 임의로 확정하지 말고 **운영진 확인 필요** 상태. 학생이 답하지 않을 때의 최종 처리 규칙은 **미확정 → Claude가 안전한 운영 방식을 제안**(임의로 정하지 않음)
- AI가 카톡을 읽거나 '다음 주'를 해석하는 기능은 지금 필요 없음

## 4. 원래 날짜 → 바뀐 날짜 자동 표시 (가장 중요)
- 보강 확정 안내(학생·강사)에 반드시: `기존 수업: 10/29 (Thu) 17:00 KST → 보강 수업: 10/30 (Fri) 17:00 KST`
- 운영진이 타이핑하지 않고 LMS 저장 정보에서 자동. 단순 취소면 취소된 원래 날짜만 정확히
- 강사 보강 수락이 필요하면 기존 승인 절차 유지, 확정 전에는 확정 안내를 만들거나 보내지 않음 (D-43)

## 5. 중복 신청 방지
학생이 LMS로 신청한 뒤 카톡으로도 같은 요청 가능 → 운영진이 같은 수업을 처리하려 하면 기존 요청 표시. 같은 요청 두 번 처리 금지, 변경권 이중 차감·보강 중복 생성 방지, 처리한 요청과 새 요청 구분, 학생·운영진 동시 클릭도 **DB 수준**에서 방지

## 6. 요청 경로·처리 이력
신청 경로(학생 LMS / 카톡 후 운영진 입력), 실제 요청자(학생), LMS 입력자(학생 본인 / 운영진 계정), 카톡 요청 시각(해당 시), LMS 입력 시각, 원래 수업 ID·날짜·시간, 요청 내용·처리 상태, 강사 확인 상태, 학생·강사 안내·발송 상태, 처리 완료·정정 시각.
- **6시간 기준은 확인 가능한 실제 학생 요청 시각**으로 판단. 시각이 불명확하면 학생에게 불리하게 판단하지 말고 확인 대상으로

## 7. 잘못 처리한 일정 복구
잘못 취소한 정규 수업 복구, 잘못 차감한 변경권·수강 회차 복구, 잘못 만든 보강 정정, 학생·강사 정정 안내 생성, 누가 언제 무엇을 고쳤는지 감사 이력. 화면 날짜만 고치고 실제 수업·변경권 데이터가 어긋나면 안 됨

## 8. 운영진 모바일 필수
학생 검색·수업 선택·취소·변경 처리·강사 확인·안내문 복사·발송 완료 기록·일정 정정까지 전부 휴대폰에서. PC 전용 금지

## 9. 개발 순서와의 관계
H23 순서·운영 DB 작업 유지. 새 시스템을 하나 더 만드는 것이 아니라 기존 취소·변경·보강 시스템의 안전장치 보완. 이미 설계·구현한 것은 중복해서 만들지 않음. 먼저 **이미 설계·구현됨 / 설계만 있음 / 새로 추가** 세 가지로 구분하고 각각 어느 단계에서 반영할지 보고
