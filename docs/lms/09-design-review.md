# 09. 설계 재검토 — 기존 시트 구조 vs 새 Supabase 구조

[08 문서](08-legacy-automation-analysis.md)의 분석을 바탕으로, 기존 자동화가 하려던 일을 새 구조가 어떻게 대신하는지와 SQL 설계를 다시 검토한 결과.

## 1. 핵심 차이 한 줄

**기존**: 같은 정보를 파일 여러 개에 복사하고 서로 맞춰 주려 했다(동기화).
**새 구조**: 정보는 DB 한 곳에만 있고, 운영자·강사·학생 화면은 같은 줄을 **각자 다른 모양으로 보여 줄 뿐**이다. 맞춰 줄 복사본이 없으므로 동기화 자체가 필요 없다. (예외: Google 캘린더는 강사가 휴대폰 캘린더 앱으로 보기 때문에 복사본을 유지 → 반영 대기열로 처리)

## 2. 누가 무엇을 입력하나 (입력 주체)

"양방향"으로 보였던 흐름은 사실 **정보마다 입력하는 사람이 다른 것**이다. 한 정보는 한 사람만 입력하고 나머지는 보기만 한다.

| 정보 | 입력하는 사람 | 보는 사람 | 저장 위치 |
|---|---|---|---|
| 학생 기본 정보, 수강등록, 담당 강사, 고정 요일·시간 | 운영자 | 강사(필요한 칸만), 학생(본인) | `students`, `enrollments`, `regular_schedules` |
| 정규 회차 | 시스템(등록 시 자동 생성) | 모두 | `lessons` |
| 수업 결과·Covered Topics·Remarks | 강사 (시스템이 아는 취소는 시스템) | 운영자, 학생(학생용 문구) | `lessons.class_status`, `class_records` |
| 수업 변경(취소) | 학생(4단계부터) 또는 운영자 대리 | 강사, 운영자 | `change_requests` → `lessons` |
| 보강 신청 | 학생(4단계부터) 또는 운영자 | 강사가 확정 | `makeup_requests` → `lessons` |
| 강사 사유 취소, 가능 시간, 막은 날 | 강사 | 운영자, (학생은 결과만) | `change_requests`, `tutor_availability`, `tutor_time_off` |
| 강사 변경, 장기 휴무 처리, 대체 수업, 기간 연장 | 운영자 | 모두 | `lessons.tutor_id`, `enrollment_extensions`, `change_requests`(batch) |
| 노쇼 신고 / 노쇼 확정 | 학생 / 운영자 | 강사, 운영자 | `no_show_reports`, `compensations` |
| 입금, 환불 | 운영자 | 운영자 | `payments`, `refunds` |
| 정산 확정 | 운영자 | 강사(승인된 것만) | `payroll_runs` |
| 정책 값 | 기준표 승인 → Claude가 코드 반영 | — | `docs/lms/policy/register.md` → `src/lms/rules/` |

## 3. 기존 기능 → 새 구조 연결표

| 기존 (시트) | 하려던 일 | 새 구조 | 달라지는 점 |
|---|---|---|---|
| Master `시트1` 학생 1행 35칸 | 학생·등록·스케줄·기간을 한 줄에 | `students` + `enrollments` + `regular_schedules` + `enrollment_periods` | 재등록·24주·연장이 칸 추가 없이 행 추가로 처리 |
| Master 1·2·3차 시작·종료일 수식 | 28일 기간 | `enrollment_periods` (코드가 계산, 테스트 39개) | 6기간 지원, 판본별 길이 |
| Master `등록수업수` 수식 | 주 수 × 요일 수 | `enrollments.lessons_purchased` (DB가 검사) | |
| Master `강사정보` + VLOOKUP | 강사 한글 이름·국가·Meet 링크 끌어오기 | `tutors` (화면에서 직접 참조) | 복사 없음 |
| `표시용 이름` 2종 (이름+ID+요일+시간 글자) | 드롭다운에서 학생 고르기 | 화면의 검색·선택 (내부는 ID) | 글자 변경으로 연결 끊김 없음 |
| Master `상태매핑표` → IMPORTRANGE | 강사·학생 시트에 상태 목록 공유 | `class_status_rules` + `status.ts` (테스트로 일치 확인) | 연결 승인(`#REF!`) 문제 없음 |
| Master `변경신청트래커` | 6시간·기간·변경권 판정 | `change_requests` + `evaluateStudentChange` | 판정 결과가 수업·변경권·강사 화면에 한 번에 반영 |
| Master `적립금이력` | 적립금 관리 | 나중 (1차 범위 밖) | — |
| 학생 수강현황 파일 (PC·모바일 탭) | 학생에게 일정·남은 변경권 보여 주기 | 학생 화면 `/my` | 파일 생성·링크 공유 없음, 로그인으로 보호 |
| 학생 시트 '진행 여부' 드롭다운 | 회차별 결과 | `lessons.class_status` → 학생용 문구 | 강사 기록이 바로 보임 |
| 학생 시트 '변경권 2회/총 2회' 값 | 남은 변경권 | `credit_balance()` 계산 | 실제 사용과 항상 일치 |
| 학생 시트 수업 노트 IMPORTRANGE | 수업 노트 링크 | `students.class_note_url` | |
| 강사 Class Record 회차 행 | 강사 일정 + 기록 | `lessons` + `class_records` (강사 화면 `/tutor`) | 강사가 바뀌면 같은 행의 담당만 바뀜 |
| Class Record `학생목록(자동)` QUERY | 담당 학생 목록 | `tutor_my_students()` | 필요한 칸만, 권한으로 보호 |
| Class Record Class Count·카운트여부 | 진행 회차 세기 | 계산 (`consumes_lesson` 합계) | 입력 칸 없음 |
| Class Record Paid (Y/N) | 정산 여부 | `payroll_items` (같은 수업 두 번 정산 불가) | |
| Class Record Course End Date | 종료일 표시 | `enrollments.final_end_date` | |
| Class Record Renewal Notice Sent | 재등록 안내 여부 | `notifications` (5단계) | |
| Weekly Schedule(KST)/(AEDT) 탭 | 강사 주간 시간표 (서머타임용 복사) | 강사 화면에서 현지·KST 자동 변환 | 서머타임 복사 탭 불필요 |
| Teacher Info 고정 시차(+2) | 강사 현지 시간 | `tutors.timezone` (IANA) | 서머타임 자동 |
| 강사 보조 캘린더 (운영자가 수동 입력) | 강사 폰에서 일정 확인 | `calendar_sync` 대기열 → 자동 반영 (5단계) | 실패 시 재시도·관리자 표시 |
| 수업 페이 계산 시트 | 월 정산 | `payroll_runs`·`tutor_contracts` (6단계) | 강사별 계약 판본 반영 |
| (없음) | — | `audit_log` | 모든 변경 이력·복구 |
| (없음) | — | `terms_versions` | 기존·신규 계약 판본 구분 |

## 4. SQL 재검토 결과 (v0.1 → v0.2)

v0.1은 이번 1차 작업에서 만든 초안이며 어떤 DB에도 적용한 적이 없어 직접 수정했다. 이전 내용은 git 기록에 남아 있다.

### 줄인 것 (같은 사실을 두 번 저장하던 곳)

| 항목 | v0.1 | v0.2 | 이유 |
|---|---|---|---|
| `price_list` 표 | DB에 가격표 | **삭제** | 가격은 홈페이지 수업료와 같은 코드 한 곳. 등록 금액은 `enrollments.amount_due`에 그날 값으로 남음 |
| `settings` 표 | 규칙값 저장 | **`feature_flags`로 축소** (켜기/끄기만) | 정책 값이 DB·코드·문서 세 곳에 생기는 것을 막음 (POL-OP-07) |
| `students.status` | 수강 중/정지/종료 | **삭제** | 수강등록에서 계산 가능 |
| `tutors.status`의 'on_leave' | 휴무 상태 | **`active` 여부만** | 휴무는 `tutor_time_off`에서 계산 |
| `payments.amount_due`, `status` | 결제할 금액·상태 | **삭제** (입금 기록만) | 결제할 금액은 등록에 한 곳. 나눠 낸 입금도 행 여러 개로 처리 |
| `enrollments.extension_days` 직접 수정 | 가능 | **연장 장부 합계로만** | 연장 사유와 일수가 어긋나지 않게 |

### 보강한 것

| 항목 | 이유 |
|---|---|
| `terms_versions` + `enrollments.terms_version` | 1판 계약(30일·변경권 4/6/10) 학생이 남아 있을 수 있음 (CF-03·04) |
| 옛 상품 이관 허용 (`legacy_label`) | 28일 검사는 현행 상품에만. 옛 등록은 실제 날짜 그대로 |
| 수업 상태 ↔ 결과 짝 검사 | 취소된 수업에 'Normal'이 들어가는 실수 방지 |
| 수업의 학생 = 등록의 학생 검사 | 다른 학생 등록에 수업이 붙는 실수 방지 |
| `change_requests.policy_refs` | 판정에 어떤 정책을 썼는지 기록 → 정책이 바뀐 뒤에도 과거 처리 근거를 알 수 있음 |
| `tutor_contracts` (정산 단계) | 강사별 계약 판본·시급 (CF-08) |
| 단계별 파일 분리 | 보강 신청(4단계)·알림·캘린더(5단계)·정산(6단계) 표는 그 단계에서만 적용 → 처음 운영할 표가 적음 |

### 그대로 둔 것과 이유

| 항목 | 이유 |
|---|---|
| `lessons.student_id` (등록에도 있음) | 같은 학생 시간 겹침을 DB가 막으려면 필요. 대신 일치 검사를 추가 |
| `class_status_rules` (TS에도 있음) | 정산·보고 SQL이 같은 값을 써야 함. 대신 TS와 같은지 자동 테스트 |
| `enrollment_periods` (계산 가능) | 변경권 장부가 기간을 가리켜야 하고, 판본마다 기간 길이가 다를 수 있음 |
| `no_show_reports`, `compensations` 별도 표 | 진행 단계(신고 → 확정)와 권리(보상권)가 수업과 다른 생애를 가짐 |

### 결과
- 표 개수: v0.1은 한 번에 29개 → v0.2는 1~3단계에 21개(변경 이력 포함), 4단계 +3, 5단계 +2, 6단계 +4 (총 30개: 계약 판본·강사 계약 추가, 가격표 삭제, 설정 → 기능 스위치로 교체).
- DB 검증 32개 → **45개** 통과, 규칙·기준표 테스트 39개 → **47개** 통과.

## 5. 더 간단한 대안이 있는가 (객관 비교)

| 기준 | A. 시트 + Apps Script 계속 (개선) | B. 시트 + AppSheet 같은 노코드 앱 | C. 기성 학원관리 SaaS | **D. Next.js + Supabase (현재 안)** |
|---|---|---|---|---|
| 대표 혼자 운영 | 지금처럼 파일 관리 부담 | 쉬움 | 쉬움 | 쉬움 (화면 3개) |
| 한 번만 등록 | 스크립트로 가능하지만 복사본 유지 필요 | 가능 | 가능 | 가능 |
| 중복 입력 없음 | 어려움 (파일마다 복사) | 시트 1개로 모으면 가능 | 가능 | 가능 |
| 휴대폰 사용 | 학생·강사에게 시트는 불편 | 앱 형태 가능 | 대체로 가능 | 맞춤 제작 |
| 엣지영어 규칙(28일 변경권, 6시간, 판본별 계약, KST 기준) | 수식·스크립트로 일부 | 표현식으로 일부, 복잡하면 한계 | **규칙을 맞출 수 없는 경우가 많음** | 그대로 구현·테스트 |
| 동시 예약 방지·원자성 | 없음 | 약함 | 제품마다 다름 | DB 제약으로 보장 |
| 오류 원인 확인·복구 | 시트 수정 기록뿐 | 제한적 | 제품 의존 | 모든 변경 이력·되돌리기 |
| 개인정보 보호 | 링크 공유 위험 | 구글 계정 권한 | 제품 의존 (해외 서버 가능) | 행 단위 권한(테스트 완료) |
| Claude와 장기 유지보수 | 가능하나 파일이 늘수록 어려움 | 노코드 설정은 Claude가 직접 다루기 어려움 | 불가 (남의 제품) | **코드·테스트로 Claude가 직접 관리** |
| 비용 | $0 | 사용자당 월 과금 | 강사·학생 수 비례 과금 | 약 $25~45/월 |
| 불필요한 기능 | 적음 | 적음 | 많음 | 필요한 것만 |

**결론: D를 유지한다.** A는 지금 문제(복사본·글자 연결·판본 관리 불가)를 그대로 안고 가고, C는 엣지영어 고유 규칙을 맞출 수 없으며, B는 규칙이 복잡해질수록 Claude가 관리하기 어렵다.

다만 D를 **더 작게** 시작하도록 조정했다.
1. 1~3단계는 운영자·강사 화면만. 학생 화면은 보기 전용부터.
2. 처음 적용하는 DB 표를 단계별로 나눔(위 4절).
3. 정책 값은 DB가 아닌 기준표 + 코드 한 곳.
4. 캘린더 쓰기·메일 발송은 스위치를 끈 채로 시작.
5. 적립금·양도·자체 결제·자동 환불·카카오 알림톡은 만들지 않음.

## 6. 남은 위험과 대응

| 위험 | 대응 |
|---|---|
| 기존 학생·강사 계약 판본을 모름 | 이관 때 `SC_UNKNOWN`/`TC_UNKNOWN`으로 넣고, 운영자 확인 목록을 자동으로 뽑음 |
| 이관 시 시트 데이터 오류(김하나 국가 불일치 같은 것)가 그대로 들어옴 | 이관 검증표에서 같은 학생의 칸끼리 다른 값을 빨간색으로 표시 |
| 병행 운영 중 시트와 DB가 갈라짐 | 3단계 시범 운영 학생은 DB만 원본, 시트는 DB에서 내보낸 읽기 전용 |
| 정책 결정 지연으로 개발 정지 | 미결 규칙은 두 선택지를 모두 구현·테스트해 두고 결정되면 값만 넣음 (지금 방식) |
