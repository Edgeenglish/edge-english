# 11. 계정·인증·결제 확인·보강 알림 설계 (2026-10-17)

근거: 정책 원본(Google Docs) **최우선 장기 제품 목표**·H10·H11·A26~A32, 기준표 POL-AC-01~06·POL-OP-15·POL-OP-18·POL-PAY-11.
상태: **설계.** 시험용 Supabase에 아직 적용하지 않은 내용은 '예정'으로 표시한다. 실제 운영 환경·학생 데이터·아임웹 설정은 건드리지 않는다.

## 0. 최우선 원칙 — 지금 LMS가 공식 홈페이지 통합 시스템의 기반

장기 목표는 공식 홈페이지 하나에서 학생이 가입·로그인·수강신청·결제·일정·변경·보강·적립금까지 쓰고, 강사·운영자도 같은 시스템에서 일하는 것이다(POL-AC-01). 그래서 지금부터 아래를 지킨다.

| 지키는 것 | 지금 구조 | 나중에 바뀌어도 그대로인 것 |
|---|---|---|
| 학생 고유 ID | `students.id`(내부 UUID) + `students.code`(`STU-0001`, 영구) | 모든 수업·수강권·결제 확인·적립금이 이 ID에 붙음 |
| 로그인 계정 | Supabase Auth 사용자 (`auth.users.id`) | 운영자가 만든 계정이든 장래 직접 가입한 계정이든 같은 종류 |
| 계정 ↔ 학생 연결 | `app_users(auth_user_id, role, student_id \| tutor_id)` 한 줄 | 가입 방식이 바뀌어도 이 연결만 만들면 됨. 학생 기록 쪽에는 계정 번호를 넣지 않음 |
| 권한 | DB가 직접 검사(RLS). 연결 없는 계정은 아무것도 못 봄 | 홈페이지가 같은 DB를 쓰면 권한 규칙도 그대로 |
| 결제 ↔ 수강등록 | `payments.enrollment_id` + 주문번호(`external_ref`) + 실제 결제 시각 | 장래 PG·아임웹 연동이 생겨도 같은 표에 '확인 방법'만 바뀜 |

**지금 하지 않는 것**: 홈페이지 전체 통합 개발, 결제 시스템 교체, 공개 회원가입, 실제 메일 발송, 유료 서비스 가입.

## 1. 계정 생성 (초기: 운영자 초대, POL-AC-03)

```
운영자: [학생 등록] (이름·개인 이메일·상품…)
  └ 서버(비밀키, 브라우저에 노출 안 됨)
      1. 운영자 권한 확인 (로그인 + TOTP 완료 세션)
      2. 같은 이메일의 계정이 이미 있으면 멈추고 운영자에게 표시 (자동 연결 안 함)
      3. auth.admin.createUser({ email, email_confirm: true })   ← 비밀번호 없음, 메일 안 보냄
      4. app_users 에 (계정 ↔ 학생) 한 줄 추가
      5. 4가 실패하면 3에서 만든 계정을 지움 (반쯤 만들어진 상태 방지)
학생: LMS 주소 → 이메일 입력 → 6자리 코드 → 로그인
```

- **초대 메일을 따로 보내지 않는 이유**: 학생은 처음 로그인할 때 받는 6자리 코드 메일 한 통이면 충분하다. 메일 양식이 하나 줄고 발송량도 준다. 안내는 지금처럼 운영자가 카톡으로 'LMS 주소 + 등록한 이메일로 로그인'을 알려 준다. 나중에 원하면 초대 메일을 추가할 수 있다.
- **이메일 1개 = 학생 1명**(POL-AC-02): 형제자매가 같은 이메일을 쓰려 하면 등록 화면이 막고 이유를 보여 준다. 보호자 계정은 나중에 `guardian_links(guardian_auth_id, student_id)` 같은 표를 **추가**하면 되고, 지금 구조를 바꿀 필요가 없다(학생 식별이 이메일이 아니라 `students.id`이기 때문).
- **학생 이메일이 바뀌면**: 운영자가 계정 이메일만 바꾼다. 학생 ID와 기록은 그대로.
- **강사**도 같은 방식(영어 화면). **운영자**도 개인 계정 + TOTP(아래 3절).

## 2. 로그인 (학생·강사·운영자 공통 1단계)

- 로그인 화면: 이메일 → `signInWithOtp({ email, options: { shouldCreateUser: false } })` → 6자리 입력 → `verifyOtp({ email, token, type: 'email' })`.
- 등록 안 된 이메일: Supabase가 `422 Signups not allowed for otp`로 거절하고 **계정·메일이 생기지 않음** — 2026-10-17 시험용 프로젝트에서 실제 확인. 화면 문구는 등록 여부와 관계없이 같게("등록된 이메일이면 코드를 보냈습니다").
- **공개 회원가입 스위치는 끈다**(A30). 위 옵션만으로는 `/signup` 경로가 열려 있기 때문. 시험용 프로젝트에서 끄는 방법: `supabase-test-setup.md` 3단계.
- 휴대폰에서는 한 번 로그인하면 오래 유지(학생). 코드 유효 시간 10분 권장.
- 실제 학생 주소로 코드를 보내려면 메일 발송 서비스(SMTP)가 필요하다(H10, D-28). 그 전까지는 가상 계정으로만 시험한다.

### 2-1. 장래 공개 회원가입을 붙일 때 (지금은 만들지 않음)

```
홈페이지 [회원가입] → 이메일 인증 → 계정 생성 (app_users 연결 없음 → 학생 데이터 0건)
  → [수강신청] (신청 기록, 학생 기록 아직 없음)
  → 결제 (아임웹 / 계좌이체) → 운영자 결제 확인
  → 운영자가 '신규 학생 생성' 또는 '기존 학생에 연결'을 선택해 확인
  → app_users 연결 + 수강권 활성화
```

- 기존 학생은 이 흐름을 거치지 않는다. 이미 계정이 있으므로 그냥 로그인한다.
- 기존 학생이 실수로 다른 이메일로 새로 가입하면, 그 계정은 연결이 없어 아무것도 보이지 않는다. 운영자가 확인 후 연결하거나 지운다. 이메일이 같다고 자동 연결하지 않는다(POL-AC-04).
- 필요해지는 추가 작업(그때 비교안·비용 보고): 가입 화면, 수강신청 기록 표, 운영자 연결 확인 화면, (선택) 휴대폰 본인인증(외부 업체 비용·계약), (장기) 홈페이지 결제 자동 연결.

## 3. 운영자 추가 인증 — TOTP (POL-AC-05)

| 항목 | 설계 |
|---|---|
| 방식 | Supabase Auth 기본 MFA(TOTP). Google Authenticator·Microsoft Authenticator 등 무료 앱. 추가 비용 없음 |
| 처음 한 번 | 운영자 로그인 → 'QR 등록' 화면 → 앱으로 QR 스캔 → 6자리로 확인 |
| 평소 | **새 기기·새 로그인 때만** 이메일 코드 + 앱 코드. 같은 기기에서는 세션이 유지되어 매번 입력하지 않음 |
| 권한 강제 | DB의 `is_admin()`이 **TOTP까지 마친 세션(`aal2`)일 때만 참**이 되도록 바꾼다(예정, migration 800). 이메일 코드만 통과한 운영자 세션은 학생 데이터를 하나도 못 봄. 화면 숨김이 아니라 DB가 막음 |
| 서버 쓰기 | 운영자 쓰기(학생 등록·결제 확인·적립금 조정)는 서버가 비밀키로 처리하되, **요청한 운영자의 세션이 aal2인지 서버가 먼저 확인**한 뒤 처리 |
| 분실 대비 | Supabase TOTP에는 복구 코드가 없다 → **인증 앱을 2개 기기에 등록**(예: 휴대폰 + 태블릿/PC 앱) 권장. 모두 잃으면 대표가 Supabase 대시보드에서 해당 인증을 지우고 다시 등록 |
| 강사·학생 | TOTP 없음(이메일 코드만). 강사에게 필요해지면 같은 방식으로 추가 가능 |

- 이전 설계(05 문서)의 '운영자 = support@ Google 로그인'은 **개인별 계정 원칙(A26)과 TOTP(A27)에 맞춰 이메일 코드 + TOTP로 바꾼다** (Claude 기술 결정, 로그인 방식을 학생·강사와 하나로 통일해 관리 단순화). 대표 Google 계정의 2단계 인증은 Google 서비스용으로 그대로 유지.
- 세션 유지 기간·민감 작업 재확인 → D-29 질문.

## 4. 결제 정보 분담 (POL-PAY-11, A29)

### 학생 화면 — 4가지만

| 표시 | 데이터 | 비고 |
|---|---|---|
| 현재 수강 등록 상태 | `enrollments.status` (결제 확인 대기 / 확정 / 수강 중 / 종료) | |
| 결제 확인 여부 | '운영자가 결제를 확인했는지' 예/아니오 + 확인 날짜 | 금액·카드 정보·주문번호는 보이지 않음 |
| 현재 수강권·수강기간 | 상품(주 n회·n분·n주), 시작~종료일, 남은 수업·변경권 | |
| 적립금 잔액 | `reward_balance` (LMS 단일 원장) | 아임웹 할인과 자동 연결되지 않음을 함께 표시(G02) |

- 학생에게는 `payments` 표를 열지 않는다(지금도 RLS로 막혀 있음). 대신 위 4가지만 돌려주는 **학생 전용 요약 함수**(예정: `student_my_enrollment_summary()`)를 둔다. 본인 확인은 함수 안에서 `my_student_id()`로 한다. 표를 통째로 여는 것보다 노출이 적다.
- 카드 영수증·거래 내역: "아임웹 주문조회에서 확인" 안내 링크만. 계좌이체 학생에게는 해당 없음(아임웹에 거래가 없음).

### 운영자 화면 — 기록·대조·누락 확인

| 기능 | 설계 |
|---|---|
| 결제 기록 | 카드(아임웹)·계좌이체 모두 운영자가 입력: 수강등록, 결제 수단, 금액, **실제 결제 시각**(A02), 아임웹 주문번호 또는 입금자명, 확인 근거 메모 |
| 확인 방법 표시 | 새 칸 `verified_via` (예정): `manual_imweb_admin`(아임웹 관리자 화면에서 확인) · `manual_bank`(통장 내역 확인) · 장래 `imweb_api` 등. **검증된 연동이 없으면 항상 '수동 확인'으로 표시** |
| 결제 ↔ 수강등록 | 결제 1건은 반드시 수강등록 1개에 연결(지금 구조). 같은 주문번호 두 번 입력 방지(지금 구조, `external_ref unique`) |
| 적립금 사용 | 사용 요청(보류) → 결제 확인 시 확정 → 미결제·취소·환불 시 복구 (지금 구조, POL-PAY-09). 카드 연계 방식은 POL-PAY-10(G05) 미정 |
| 결제 누락 | '결제 확인 대기' 상태로 n일 지난 등록, 재등록 의사는 있는데 결제가 없는 학생 → 처리할 일 목록에 표시. 기준 일수는 Claude 기본값 3일(변경 가능, 대표 확정 아님) |

## 5. 보강 자동 리마인더 이메일 (POL-OP-18, A28)

```
보강 확정 (lessons kind='makeup', state='scheduled')
  └ DB 트리거가 notifications 에 2줄 예약
      makeup:{수업ID}:{시작시각}:24h   send_after = 시작 - 24시간
      makeup:{수업ID}:{시작시각}:2h    send_after = 시작 - 2시간
보강 시간 변경 → 예전 2줄 'canceled', 새 시각으로 2줄 새로 예약 (dedupe_key에 시작시각이 들어가 겹치지 않음)
보강 취소     → 남은 예약 'canceled'
발송기 (5분마다, Supabase Cron → Edge Function)
  1. send_after 지난 'queued' 행을 잠그고 가져옴 (두 발송기가 같은 행을 못 잡음)
  2. 보내기 직전에 수업을 다시 확인: 아직 예정 상태이고 시작 시각이 예약 때와 같을 때만 발송
  3. 결과 기록: sent / failed(+오류, 재시도 횟수) — 최대 3회 재시도 후 운영자 화면에 표시
```

- **중복 방지**: `dedupe_key` 유일 제약(이미 있음) + 발송 직전 재확인.
- **이미 지난 시점**: 보강을 시작 24시간 이내에 잡으면 24시간 전 메일은 보내지 않음. 2시간 이내면 둘 다 보내지 않음(D-30 확인).
- **시간 표기**: 'KST 기준 시각'을 항상 쓰고, 학생 시간대가 한국이 아니면 현지 시각을 함께 표시(`students.timezone`).
- **수신 설정**: 서비스 안내 메일이라 기본 켬, 학생이 LMS에서 끌 수 있게(D-30). 광고·마케팅 메일과 섞지 않음.
- **Vercel Hobby Cron은 쓰지 않음**: 하루 1회·시각 오차 최대 약 1시간이라 2시간 전 알림에 부적합(정책 원본 A28 조사). Supabase Cron(pg_cron) + Edge Function을 쓰며 무료 요금제 안에서 가능할 것으로 보이나 **시험 때 실제로 확인**한다.
- **발송량 추정**: 보강 1건당 2통. 예를 들어 한 달 보강 100건이면 200통 + 로그인 코드 메일. 정책 원본 A28에 기록된 무료 한도(Resend 월 3,000통, Brevo 일 300통)라면 2회 발송이 무료 범위일 가능성이 높다. 업체 비교·가격 재확인은 메일 연결 시점에 한다(D-28).
- 정규 수업 리마인더 없음.

## 6. 바뀌는 DB (예정 — 시험용 DB 적용 전 대표 승인)

모두 **기존 표에 칸·함수·트리거를 더하는 변경**이고 기존 데이터를 옮기거나 지우지 않는다. 로컬 재현 테스트(`npm run test:db`)를 먼저 통과시킨 뒤 SQL Editor 실행 안내를 드린다.
