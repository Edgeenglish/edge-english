## 3. 발견 사항

### A. 실제 기능 오류

#### A-01 · 높음 — 학생 화면에서 정상 취소 저장이 실패함

- **위치:** 학생 화면 → 홈 → 수업 변경·취소 → 11/10 회차 → 취소하고 보강 시간 고르기
- **재현:** STU-0027의 첫 정규 회차를 선택하고 확인을 눌렀더니 “요청 받은 시각이 지금보다 늦습니다.” 오류가 나왔습니다. DB의 회차는 scheduled 그대로였고 취소·변경권 차감도 저장되지 않았습니다. 같은 시험 학생은 운영진 화면에서 정상 취소할 수 있어 학생 경로 문제로 구분됩니다.
- **영향:** 학생이 정책상 가능한 취소·보강 요청을 직접 완료할 수 없습니다.
- **개선:** 화면의 요청 시각을 서버 시각 기준으로 만들고, 제출 시 동일 기준으로 검증하세요. 사용자에게 내부 시간 비교 오류를 노출하지 말고 원인과 재시도 방법을 표시하세요.
- **문구:** 현재 “요청 받은 시각이 지금보다 늦습니다.” → “요청을 저장하지 못했어요. 화면을 새로고침한 뒤 다시 신청해 주세요.” 서버 시각 차이로 차단됐다면 운영자 로그에 원인을 남기세요.
- **정책 충돌:** H26의 학생 셀프서비스 요청과 6시간 취소 규칙의 정상 이행을 막으므로 충돌.

#### A-02 · 높음, 재확인 필요 — 회차 날짜 입력과 저장 상태가 맞지 않음

- **위치:** 신규 등록·매칭의 특정 회차 날짜 변경, 학생 상세의 시작 전 날짜 변경
- **재현:** 현재 시험 빌드의 시작 전 날짜 변경 창에서 2회차 날짜를 입력했을 때 입력칸 값은 보였지만 저장 버튼이 활성화되지 않았습니다. 날짜 입력과 파생 미리보기가 동기화되지 않는 징후가 있었습니다. 이전 Work 재현에서는 날짜 11/18을 입력하고 시각 10:30을 바꿔 적용하자 날짜는 원래 11/17로 남고 시각만 변경됐습니다. 다만 이 세션에서는 브라우저의 실제 날짜 선택기를 통한 독립 수동 확인을 완료하지 못해 보편 재현으로 단정하지 않습니다.
- **영향:** 첫 수업일 또는 특정 회차를 다른 날로 옮겼다고 생각했는데 실제 저장은 원래 날짜로 남을 수 있습니다.
- **개선:** 날짜 state, 미리보기, 저장 payload를 동일한 값으로 묶으세요. 입력값과 저장될 날짜가 다르면 저장을 막고 실제 저장값을 확인 화면에 표시하세요. 실제 터치 날짜 선택기에서 DB까지 재검증하세요.
- **문구:** 저장 전 “변경 날짜 11/17”처럼 서버에 저장될 날짜를 명시하고, 날짜 선택이 반영되지 않았으면 “날짜를 다시 선택해 주세요” 표시.
- **정책 충돌:** H26(61)·(62)의 회차별 날짜 변경 가능 정책을 불완전하게 이행할 위험.

#### A-03 · 높음 — 아직 적용 전인 정규 일정 변경을 UI로 되돌릴 수 없음

- **위치:** 운영진 학생 상세 → 정규 일정 수정
- **재현:** STU-0004 화요일 12:30을 11/9부터 12:00으로 실제 저장해 8회가 이동했습니다. 복구를 위해 화요일 12:30을 다시 선택하자 화면은 “현재 일정과 동일”로 간주해 저장을 비활성화했습니다. DB에는 화요일 12:00, 목요일 12:30의 11/9 시작 일정이 남았습니다.
- **영향:** 시행 전 일정 실수를 관리자가 되돌릴 수 없습니다. 시험 상태에서도 앞으로 예정된 회차가 잘못된 시각으로 남아 있음.
- **개선:** 화면이 현재 유효 일정과 향후 예약 변경을 구분하게 하고, 시행 전 변경을 취소·수정하는 정상 경로를 제공하세요. 원래 시간으로 복원하면 기존 미래 변경 row와 이동 수업도 같이 되돌아가야 합니다.
- **문구:** “현재 적용 중”과 “11/9부터 적용 예정”을 별도 표시하고, 예정 변경에는 “예정 변경 취소”를 제공.
- **정책 충돌:** 정규 일정 변경 자체는 허용되지만, 취소·수정 경로가 없어 운영 안정성에 충돌.

#### A-04 · 보통, 저장 실패로 재현되지 않음 — 강사 휴무 날짜 폼

- **위치:** 운영진 → 강사 휴무 → 새 휴무 입력
- **관찰:** Blair를 선택하고 시작일·종료일·사유를 채웠을 때 날짜 입력값이 보이는데 저장 버튼이 비활성 상태로 유지됐습니다. 브라우저 자동화에서 날짜 입력 이벤트가 실제 네이티브 선택기와 다를 가능성이 있어 저장 실패로 단정하지 않았고, DB 변경은 없습니다.
- **영향:** 실제 운영자가 같은 상태를 만나면 휴무 등록을 못 하거나 원인을 알 수 없음.
- **개선:** 실제 모바일·PC 네이티브 날짜 선택기로 같은 날짜 또는 기간을 입력해 재현 확인. 필수 조건이 충족된 뒤에도 저장이 비활성이라면 누락 조건을 바로 안내.
- **문구:** “저장할 수 없음” 대신 “강사·시작일·종료일을 선택해 주세요” 또는 실제 차단 사유.
- **정책 충돌:** 휴무일 입력의 업무 목적과 충돌 가능. 현재는 미확정.

### B. 심각한 UX 문제

#### B-01 · 높음 — 결제 대기 등록을 “수강 예정” 및 0/4회로 표시

- **위치:** 운영진 학생 상세 STU-0025
- **재현:** 결제 대기 과정은 정규 일정 0건·수업 0건·pending_payment인데 화면 상단은 “수강 예정”, “남은 정규 0/4”, 종료일을 표시합니다.
- **영향:** 운영진이 이미 수업이 잡힌 학생으로 오해하거나 4회가 사라졌다고 생각할 수 있음.
- **개선:** 결제·강사 배정·일정 확정 상태를 구분하고 수업 예정일은 실제 일정이 있을 때만 표시.
- **문구:** “수강 예정” → “결제 확인 전 · 강사 배정 전”; “남은 정규 0/4” → “결제 확인 후 4회 생성”.
- **정책 충돌:** 결제 확인 전 매칭 보류라는 운영 원칙과 표시가 충돌.

#### B-02 · 높음 — “제안 문구 복사” 동작 뒤 제안 발송 완료처럼 기록

- **위치:** 신규 등록·강사 매칭의 강사 제안 상태
- **재현:** “아직 → 제안 문구 복사”를 선택했을 때 실제 외부 메시지를 보내지 않았는데 화면에 “제안 보냄” 시각이 기록됐습니다.
- **영향:** 운영자가 강사에게 실제 연락했다고 오인해 매칭 대기를 놓칠 수 있음.
- **개선:** 문구 미리보기·복사와 실제 전송 여부를 별도 상태로 관리. 이 LMS에서는 수동 발송이 기본이므로 복사만으로 sent_at을 기록하지 마세요.
- **문구:** “제안 보냄” → “문구 복사됨 · 아직 발송 안 함”; 발송 확인 뒤 “강사에게 보냄”.
- **정책 충돌:** 실제 발송·확인 추적 요구와 충돌.

#### B-03 · 보통 — 운영진의 “변경” 버튼이 실제로 수업 취소를 저장

- **위치:** 운영진 수업 변경 화면
- **재현:** 실제 취소 흐름에서 버튼 “변경”을 클릭하면 취소 및 변경권 차감이 저장됐습니다.
- **영향:** 버튼만 보고 날짜 변경이라고 예상한 운영자가 실수로 취소할 수 있습니다.
- **개선:** 현재 선택된 작업과 저장 결과를 버튼 문구에 반영.
- **문구:** “변경” → “수업 취소 저장”; 날짜를 바꾸는 흐름에서만 “변경 저장”.
- **정책 충돌:** 기능 정책은 충돌하지 않으나 실수 방지 목적에 부적합.

#### B-04 · 보통 — 보강 신청 저장 결과가 바로 보이지 않음

- **위치:** 운영진 수업 변경·보강
- **재현:** “신청” 클릭 뒤 버튼이 비활성화됐고 즉시 성공 문구는 보이지 않았습니다. DB에는 requested, 강사 To do에는 신청 1건이 생성됐습니다.
- **영향:** 운영자가 저장됐는지 몰라 같은 신청을 반복하거나 화면을 이탈할 수 있음.
- **개선:** 성공·중복·실패를 화면에 즉시 표시하고 요청 내역에 신청자·시각·후보를 남기세요.
- **문구:** 버튼이 비활성화되는 것만으로 처리하지 말고 “강사에게 확인 요청을 보냈어요. 답변 대기 중” 표시.
- **정책 충돌:** 업무 정책은 충돌하지 않으나 상태 전달이 불충분.

### C. 일반 UX 개선

#### C-01 · 보통 — 직접 입력 선택 뒤 Google Form 정보 영역이 계속 노출

- **위치:** 신규 학생 등록
- **재현:** “신청서 없이 직접 입력”을 선택해도 Google Form 관련 입력 영역이 화면에 남습니다.
- **영향:** 처음 사용하는 운영자가 직접 입력과 폼 제출 둘 다 필요하다고 생각할 수 있음.
- **개선:** 입력 모드 선택에 따라 해당 모드에 필요한 필드만 보여 주세요.
- **문구:** 선택지를 “Google Form 제출 내용을 가져와 등록” / “신청서 없이 직접 등록”으로 바꾸고 다른 모드 입력란은 접기.
- **정책 충돌:** 없음.

#### C-02 · 보통 — 등록 화면의 진행 단계가 PC에서 한 화면에 길게 이어짐

- **위치:** 신규 등록
- **재현:** PC는 네 단계가 한 긴 화면에 표시되고 휴대폰은 한 단계씩 진행합니다.
- **영향:** 입력이 복잡한데 현재 단계·빠진 필드·최종 확인 위치가 묻힐 수 있음.
- **개선:** PC도 단계별 진행 표시를 두고, 수업 목록·비용 확인을 최종 단계에 요약.
- **문구:** “1 학생 → 2 수강권 → 3 수업 일정 → 4 결제 확인” 고정 진행 표시.
- **정책 충돌:** 없음.

#### C-03 · 보통 — 대시보드의 가로 카드와 강사 주간표가 모바일에서 좁음

- **위치:** 운영진 Home, 강사 Availability
- **재현:** 전체 페이지 가로 넘침은 보이지 않았지만 운영진 요약 카드가 가로 스크롤되고 마지막 카드가 일부 잘렸습니다. 강사 가능 시간 7일 칸은 휴대폰 폭에서 요일·시간 라벨이 좁게 표시됨.
- **영향:** 스와이프 가능한지 모르거나 날짜·상태를 잘못 읽을 수 있음.
- **개선:** 카드 2열 또는 세로 스택, 요일 칸은 모바일에서 날짜 목록형으로 전환하거나 현재 선택 요일을 크게 보여 주세요.
- **문구:** 필요하면 “옆으로 밀어 더 보기” 안내를 한 번 표시.
- **정책 충돌:** 휴대폰에서 원활해야 한다는 H26(46) 개발 요구와 부분 충돌.

#### C-04 · 낮음 — 학생의 신청 내역·학습자료가 빈 화면처럼 보임

- **위치:** 학생 화면 → 신청 내역, 학습자료
- **재현:** 신청 내역은 제목만 있고 빈 상태 안내가 없음. 학습자료는 교재 소개 링크만 있음.
- **영향:** 로딩 오류인지 아직 자료가 없는지 알기 어려움.
- **개선:** 빈 상태 안내와 다음 행동을 표시.
- **문구:** 신청 내역 “아직 신청한 내용이 없어요.” / 학습자료 “강사님이 교재를 정하면 여기에 표시돼요.”
- **정책 충돌:** 없음.

#### C-05 · 낮음 — 메뉴와 처리 버튼이 동작을 충분히 말하지 않음

- **위치:** 운영진 대시보드 To do·처리 내역
- **재현:** 여러 카드가 동일한 “처리 종료” 버튼을 사용하고, 재열기 후에도 업무 종류에 따라 종료 라벨이 다르게 보이지 않음.
- **영향:** 종료가 해당 업무 완료인지 카드 숨김인지 처음 보는 사람이 예상하기 어려움.
- **개선:** 카드 종류에 따라 완료 동작을 명명하고 처리 내역에는 원래 작업명·완료 상태를 함께 표시.
- **문구:** “처리 종료” → 업무별 “대조 완료”, “안내 발송 기록”, “기록 완료”.
- **정책 충돌:** 정책 판단과는 무관, 업무 UX 개선.

#### C-06 · 낮음 — Handoff 상단 정책 번호가 오래됨

- **위치:** docs/lms/handoff.md
- **재현:** 상단에는 최신 H26 번호 (55)라고 되어 있으나 본문은 (65)까지 기록. Google 정책 원본은 (67).
- **영향:** 다음 작업자가 최신 정책·요청을 놓칠 수 있음.
- **개선:** Handoff 상단 최신 번호·날짜·운영 미반영 경고를 갱신하고 테스트 배포 기준을 같이 기재.
- **정책 충돌:** 정책 자체가 아닌 기록 최신성 문제.

### D. 미구현·정책 결정 필요

#### D-01 · 높음 — 첫 수업 후 강사 To do가 정책 원본 H26(67) 요구를 반영하지 않음

- **위치:** 강사 Home → To do, Students, Student profile
- **재현:** Blair 화면의 To do에는 Class Record 미기록 5회만 표시됐습니다. 첫 수업 이후 영어 레벨, Wants to improve 직접 확인, Class style/Type of class, 필요한 교재 선택을 위한 To do는 확인되지 않았습니다. 학생 프로필에는 항목을 볼 수 있지만 작업 목록으로 안내하지 않습니다.
- **영향:** 강사가 첫 수업 뒤에 필수 정보를 빠뜨리거나, 운영진이 반복 리마인드해야 함.
- **개선:** 첫 수업 후 학생별 완료 상태를 표시하고 이미 기록된 항목은 다시 요청하지 않는 To do를 추가하세요. Job/Hobbies/Interests 등 사전 카카오톡 답은 강사에게 중복 입력시키지 않습니다.
- **추천 문구:** “첫 수업 후 학생 정보 확인” 아래에 “영어 레벨 평가 · 학습 목표 직접 확인 · 수업 방식 결정 · 필요 시 교재 선택 · Class Record 작성”.
- **정책 충돌:** 정책 원본 H26(66)·(67)의 명시된 역할 구분과 요구에 현재 화면이 미반영.

#### D-02 · 보통 — 자유 입력 시간과 회차별 날짜 변경은 실제 사용자 경로를 더 검증해야 함

- **위치:** 신규 등록·매칭 일정 단계
- **재현:** 화면에서 요일·시간 선택과 특정 회차 변경 UI를 확인했으나, 자유 텍스트 시각 입력과 모바일 네이티브 날짜 선택 후 서버 저장을 완주하지 못함. 날짜 state·저장 미리보기는 A-02로 분리.
- **영향:** 사용자가 기존 선택지에 없는 정확한 시간·첫 수업일을 넣을 수 있는지 보장할 수 없음.
- **개선:** 대표 시안 H26(61)·(62) 기준으로 PC·모바일에서 요일/시간 선택, 첫 수업일, 특정 회차를 각각 한 건 저장해 DB·강사 현지 시간과 대조.
- **정책 충돌:** 무료 시작 전 조정과 기존 변경권 정책을 구분해야 함.

#### D-03 · 보통 — 일반 학생 로그인과 실제 권한 경계는 검증하지 못함

- **위치:** 학생 로그인, 강사 로그인, 대체강사 접근 권한
- **재현:** 운영자 보기만 사용. 별도 학생·강사 로그인·로그아웃·대체강사 종료 후 접근 회수는 이번 세션에서 수행하지 않음. Blair 학생 프로필에서는 운영 메모가 보이지 않았지만 이 확인만으로 RLS 전체를 통과 처리하지 않음.
- **영향:** 실제 역할별 권한·세션 격리를 확인하지 못함.
- **개선:** 시험 전용 계정으로 각 역할의 정상 로그인 경로에서 자기 데이터·타인 데이터·관리자 메모·대체 접근 종료 후 차단을 확인.
- **정책 충돌:** 개인 계정·역할 권한 분리 목표와 관련.

#### D-04 · 보통 — 실제 결제·급여·이월은 이번 검증 범위 밖 또는 미구현

- **위치:** 수강·결제·정산
- **재현:** STU-0027은 시험 DB를 위한 1원 가상 입금 표시일 뿐 실제 결제 승인·환불·급여 마감은 시험하지 않음.
- **영향:** 현재 저장 흐름 통과가 재등록 결제·이월·급여 정산의 완료를 뜻하지 않음.
- **개선:** 별도 정책·회계 검증 후 전용 시험 흐름을 마련.
- **정책 충돌:** H26(56) 및 이전 QA에서 남긴 미구현 범위와 일치.

#### D-05 · 보통 — R-20 저장 중 이탈/재조회 결과는 최신 시험 빌드에서 독립 재검증되지 않음

- **위치:** 운영진 저장 띠·뒤로가기·새로고침
- **이력:** 이전 최종 QA 보고서(b16c683)는 새로고침 뒤 DB 저장 성공인데도 실패/미확정 안내가 남는 오류를 보고했습니다. 현재 시험 배포는 14f83ea로 더 새롭지만, 이번 전체 감사에서는 지연 저장·새로고침·재접속을 같은 저장 식별자로 끝까지 재실험하지 않았습니다.
- **영향:** 과거 배포 차단 오류가 현재 수정됐다고 단정할 수 없음.
- **개선:** 성공·거절·타임아웃 각각을 PC·모바일에서 재현하고 DB 상태 및 재접속 안내가 일치해야 통과 처리.
- **정책 충돌:** 저장 결과 정확성과 중복 처리 방지 요구와 관련.

엣지영어 LMS 독립 QA 결과를 반영해 주세요. 작업은 lms-test와 시험 DB에서만 진행하고 운영 DB·운영사이트에는 저장·migration·배포하지 마세요. 고객 카카오톡·강사 WhatsApp을 실제 발송하지 마세요. 코드 수정 뒤에는 시험 DB 저장과 UI를 서로 대조하고, 시험 데이터는 정상 화면 경로로 가능한 만큼 복구하되 감사 이력을 지우지 마세요.

## P0: 실제 오류와 저장 정확성

1. 학생 화면의 취소/보강 요청을 재현하세요. 시험 학생에서 11/10 회차 선택 후 “취소하고 보강 시간 고르기” 제출 시 “요청 받은 시각이 지금보다 늦습니다.”가 나면서 DB 저장이 거절됐습니다. 서버 시각을 기준으로 요청을 만들고, 6시간 경계는 정책과 동일하게 판정하세요. 성공·실패 뒤 수업 상태, credit_ledger, 학생 화면 및 운영진 화면이 모두 일치해야 합니다.

2. 신규 등록·매칭·학생 상세의 개별 회차 날짜 변경에서 날짜 입력, 미리보기, 저장 요청, DB 날짜를 같은 값으로 유지하세요. 날짜를 고른 뒤 저장 버튼이 비활성인 상태, 또는 시각만 저장되고 날짜가 원래 날짜로 남는 상태를 방지하세요. 실제 PC와 모바일 네이티브 날짜 선택기로 저장한 뒤 새로고침·DB·학생/강사 화면을 확인하세요. 저장 버튼에는 실제 적용될 날짜를 보여 주세요.

3. 정규 일정의 미래 변경을 적용일 전 취소·수정할 수 있게 하세요. STU-0004의 화요일 12:00 변경이 2026-11-09부터 남아 있고, 원래 12:30을 선택하면 “현재 일정과 동일”로 저장이 비활성화되는 상태를 재현하세요. 예정 변경 취소 시 future schedule row와 이동 회차가 안전하게 원복되고 변경권·수업 수가 바뀌지 않는지 확인하세요. 기존 STU-0004 시험 변경도 시험 화면에서 복구하세요.

4. 운영진 저장의 성공/실패/타임아웃/새로고침/뒤로가기 결과를 최신 lms-test에서 다시 검증하세요. 이전 QA에서 새로고침 후 서버 저장은 성공했는데 안내가 미확정으로 남은 이력이 있습니다. 각 저장 요청을 서버 데이터와 다시 연결해 재접속 뒤 정확히 판정하고 중복 저장을 막으세요. 해당 전 과정은 DB 대조를 기록하세요.
