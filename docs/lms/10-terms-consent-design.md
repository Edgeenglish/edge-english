# 10. 수업 안내 확인·동의 기능 설계 (초안 v0.1, 2026-10-16)

정책: POL-OP-12 (변경 제안) · 결정 대기: D-22~D-26 · DB 초안: `supabase/migrations/20261016000400_lms_terms_consent.sql` · 화면 시안: https://claude.ai/artifact/PFkJbUuMy8CLJtamJxYQBK (원본 `previews/consent-drafts/`)
**대표가 범위·디자인을 고르기 전에는 실제 서비스·운영 DB에 적용하지 않는다.** 법률 관련 내용은 모두 '미확인'이며 전문가 확인 대상이다.

## 1. 목적

- 지금: 학생마다 계약서 또는 안내서 이미지를 카톡으로 보내고, 받았는지·읽었는지 확인할 방법이 없음.
- 바꾸려는 것: 링크 하나로 **학생 본인이 읽고 체크하고 동의** → 누가, 어느 등록에서, **어느 판의 어떤 원문**에, 언제 동의했는지 자동 기록.
- 하지 않는 것: 기존 학생의 계약 조건을 바꾸기, 동의 안 한 학생의 수업·등록 막기, 클릭 동의로 모든 법적 요건이 충족된다고 가정하기.

## 2. 이용 흐름

| 단계 | 운영자 | 학생 | 자동 |
|---|---|---|---|
| 1 | LMS에 신규·재등록 저장 | | 그 등록에 '확인 요청'이 생김 (지금 게시된 수업 안내 판) |
| 2 | **[링크 복사]** 한 번 → 카톡 채널 대화에 붙여넣기 (지금 이미지 보내는 것과 같은 수고) | | 학생 이메일로 같은 링크 발송 (무료, 기능 스위치로 켬) |
| 3 | | 링크 열기 → 이메일 6자리 코드로 로그인 (한 번 로그인하면 휴대폰에서 유지) | |
| 4 | | 안내 읽기 → 필수 항목 체크 → '확인하고 동의합니다' | 서버가 본인 확인 후 동의 시각·문서 해시 기록 |
| 5 | 대시보드 '확인 안 한 학생 N명'에서 확인. 필요하면 링크 다시 복사 | 내 화면에서 동의한 안내를 언제든 다시 봄 | |

링크에는 요청 번호만 들어 있다. **로그인한 본인이 아니면 내용도 안 보이고 동의도 안 된다** (DB가 `auth.uid()`로 직접 확인. 운영자·강사·다른 학생도 대신 동의 불가 — 테스트로 확인).

### 결제 전에 보여 줘야 하나 (D-24)
지금 순서는 결제 → 신청서 → 매칭 (POL-PAY-02)이라, LMS 등록 뒤 받는 동의는 **결제 후 동의**가 된다. 결제 후 동의가 그 등록 조건으로 효력이 있는지는 미확인(법률). 보완안: 같은 원문을 홈페이지 공개 페이지(예: `/class-guide`, 판 번호 표시)로 올리고 수업료·결제 안내에서 결제 전에 링크 → LMS 동의는 '받은 것을 확인'하는 기록. 운영 부담은 거의 없음(원문이 하나).

## 3. 카카오톡 자동 발송 검토

| 방법 | 가능 여부 | 필요한 것 | 비용 | 운영 부담 |
|---|---|---|---|---|
| **링크 복사 → 카톡 채널 대화에 붙여넣기** | ✅ 지금 바로 | 없음 | 0원 | 학생당 10초 (지금 이미지 보내기와 같음). 확인은 자동 |
| **이메일 자동 발송** | ✅ | 발송용 메일 서비스 연결 (Supabase 기본 메일은 시간당 발송 수가 매우 적어 운영용으로 부족) | 소규모는 무료 구간이 있는 서비스가 많음 — **금액·한도 확인 필요** | 없음 |
| 카카오톡 채널 1:1 대화 자동 발송 | ❌ | 채널 1:1 대화를 프로그램으로 보내는 공개 방법은 확인하지 못함 | — | — |
| **카카오 알림톡** | ◐ 가능하나 준비 필요 | 비즈니스 인증 채널 + 공식 발송 대행사 가입 + 메시지 틀(템플릿) 사전 심사 + 학생 휴대폰 번호 | 건당 과금(대략 수~십여 원대로 알려져 있으나 **업체별 확인 필요**) + 대행사 조건 | 처음 설정 며칠, 문구 바꿀 때마다 재심사. **해외 번호 수신 가능 여부 미확인** |
| 카카오 로그인 | ◐ 나중 | 카카오 개발자 앱 등록·검수 | 무료 | 학생 로그인은 쉬워지지만 동의 기록 자체와는 별개 |

**추천: 1단계는 '링크 복사 + 이메일'(0원).** 학생 수가 늘어 붙여넣기도 부담되면 그때 알림톡을 검토. 알림톡은 비용·심사·해외 학생 문제 때문에 지금 들일 이유가 약함.

## 4. 기록하는 것 (요청하신 항목 ↔ DB)

| 요청 항목 | 저장 위치 |
|---|---|
| Student ID · 수강등록 ID | `consent_requests.student_id`(→ `students.code` STU-0001), `enrollment_id` |
| 동의한 안내서·약관의 판 | `terms_documents.terms_code`(판 코드) + `revision` |
| 동의 당시 보여 준 문서 원본 | `terms_documents.body_md`(텍스트 원문) · `assets`(이미지 파일 경로·해시) · `content_sha256`(DB가 계산). 게시 후 고칠 수 없음, 고치면 새 판/새 revision |
| 동의 날짜·정확한 시각 | `consent_events.acted_at` (서버 시각, UTC 저장·KST 표시) |
| 동의 여부 · 철회 · 재확인 이력 | `consent_events.action` = viewed / accepted / withdrawn — **쌓기만 하고 고치거나 지울 수 없음**. 재확인은 새 요청(reason = reconfirm·policy_change) |
| 체크한 항목 | `consent_events.checked_items` (필수·선택 구분) |
| 그 순간 문서 | `consent_events.document_sha256` (문서 행이 바뀌지 않았다는 이중 확인) |
| 누가 기록했나 | `actor_auth_id`, `actor_role` (동의는 학생만, 철회는 학생 또는 운영자가 사유와 함께 대신 기록) |
| 관리자 확인 | `consent_status` 보기(요청마다 마지막 상태·동의 시각·처음 열람 시각). 학생은 본인 것만 보임(RLS) |

과거 문서(계약서·이미지 안내서)를 언제 어떻게 받았는지는 기존 `terms_deliveries`에 그대로 기록하고, 온라인 동의만 위 표들에 기록한다. 같은 학생·등록·판 코드(`terms_versions`)를 함께 쓰므로 중복 관리가 없다.

**기록하지 않는 것(제안)**: IP 주소·기기 지문은 기본으로 저장하지 않음 (개인정보 최소 수집). 분쟁 대비로 필요하면 D-25에서 결정 — 저장하면 보관 기간도 함께 정해야 함.

## 5. 2장짜리 안내서(G20260709)를 어떻게 저장하나

| 무엇 | 저장 |
|---|---|
| 판 코드 | `G20260709` (kind = guide) — **2장이 한 판**. 1장만 바뀌어도 새 판 코드 |
| 원문 | `terms_documents` revision 1, format = image_set, assets = [1장, 2장] 각각 파일 경로·sha256 (`docs/lms/original/guide-G20260709/` 의 2026-10-16 대화 첨부본: `b6412ba7…`, `d4c4b62e…`). 검색·확인용 옮긴 글은 [`policy/guide-2026-07-09-review.md`](policy/guide-2026-07-09-review.md) 2절 |
| 학생에게 전달된 사실 | `terms_deliveries`에 경로별로 따로: 카톡 발송(kakao) · 학생 시트 게시(student_sheet), 각각 날짜·결제 전후 |
| 온라인 동의 | **G20260709 원문 그대로 온라인 동의를 받는 것은 비추천** — 24주가 없고(CF-23), 환불·장기 연기가 없으며(CF-26), 이월·고정 시간 문구가 계약서와 다름(CF-24). 새 텍스트 판을 만든 뒤 그 판으로 받기 |
| 새 판 | 예: `CT2026A` (kind = class_terms), 텍스트 원문 + 판 번호·시행일을 화면에 표시. FAQ·홈페이지 공개 페이지도 같은 원문에서 만들어 문구가 갈라지지 않게 함 |

주의: 학생 시트 안 이미지를 새 판으로 **덮어쓰면** 예전 학생이 무엇을 봤는지 알 수 없게 됨 → LMS 전환 전까지 시트 이미지는 바꾸지 않거나, 바꾼 날짜를 기록 (Q-7).

## 6. 신규·재등록·기존 학생 구분

| 학생 | 확인 요청 | 보여 줄 판 | 지켜야 할 것 |
|---|---|---|---|
| 신규 (LMS 도입 후) | 등록 저장 시 자동 생성 (reason = new) | 그때 게시된 판 | — |
| 재등록 (LMS 도입 후) | **D-24 결정**: (가) 판이 바뀐 때만 (나) 매번 | 그때 게시된 판 | 이전 등록의 동의는 그대로 남음 |
| 기존 학생 ① 계약서 | **자동 생성 안 함** | — | 계약 판본 존중. 새 안내를 보여 주더라도 "이번 등록부터 적용"인지는 D-22 |
| 기존 학생 ② 안내서만 · ③ 계약 후 안내서만 | 자동 생성 안 함 (D-22 결정 후 운영자가 선택) | — | 안내서를 다시 보여 준다는 이유로 과거 조건을 바꾸지 않음 |

화면 문구 원칙: 동의 화면에 **"이 확인은 ○회차 수강등록(시작일 ~ 종료일)에 대한 것입니다"**를 표시해 어느 등록의 조건인지 분명히 함. 기존 계약과의 관계를 화면에 어떻게 적을지는 법률 확인 후 결정.

**동의 안 한 학생**: 수업·등록을 자동으로 막지 않는다 (DB에 연결 자체가 없음 — 테스트로 확인). 운영자 화면에 '미확인'으로 표시하고, 다시 보낼지·어떻게 처리할지는 대표 결정 (D-24).

## 7. 이미지 안내 vs 텍스트 안내

| 기준 | 이미지 (지금) | 텍스트 (제안) |
|---|---|---|
| 휴대폰 가독성 | 확대해야 읽힘, 2장 넘겨 보기 | 화면 폭에 맞게 줄바꿈, 글자 크기 조절 |
| 접근성 | 화면 낭독기가 못 읽음. '불가'를 이모지(🙅)로만 표현 | 낭독기·번역기 가능. 뜻을 글로 명시 |
| 판 관리 | 이미지에 판 표시 없음, 바꿔 끼우면 구분 불가 | 판 번호·시행일 표시, 해시로 원문 고정 |
| 수정 | 디자인 파일 수정 → 다시 내보내기 | 원문 수정 → 새 판 게시 (FAQ와 같은 원문) |
| 항목별 체크 | 불가 | 핵심 조항마다 체크 가능 |
| 시각 효과 | 강조색·디자인 | 강조 표시·요약 카드로 충분히 가능 |

추천: **텍스트를 원본으로, 핵심 요약 카드 + 전체 원문 펼치기.** 이미지가 필요하면 텍스트에서 만든 보조 자료로만.

## 8. 별도 동의와 분리

| 항목 | 성격 | 화면 |
|---|---|---|
| 수업 안내·수강규정 확인 | 필수 (class_terms) | 필수 체크 |
| 개인정보 수집·이용 안내 | 법정 고지·동의 대상일 수 있음 (privacy_notice) — **별도 문서·별도 체크**. 해외 강사에게 학생 정보 제공 시 국외 이전 고지·동의가 필요한지 **미확인** | 따로 |
| 마케팅·소식 수신 | 선택 (marketing) — 체크 안 해도 수강에 영향 없음 | 따로, 기본 해제 |

하나의 '전체 동의' 체크로 묶지 않는다. 시안 중 '전체 동의' 버튼이 있는 경우에도 개별 체크가 기록된다.

## 9. 법률 검토가 필요한 것 (모두 미확인 — Claude가 판단하지 않음)

1. 예전 계약(9조 유무별)이 안내서만 받은 재등록분에도 이어지는지 (POL-OP-10)
2. 결제 후 받은 안내서·온라인 동의가 그 등록의 조건이 되는지 (POL-OP-11, D-24)
3. 클릭 동의(전자적 동의)의 증명력과 필요한 기록 범위 (IP·기기 정보 필요 여부, D-25)
4. 약관 명시·중요 내용 설명 의무: 환불·장기 연기처럼 학생에게 중요한 조건을 어떻게 보여 줘야 하는지
5. 온라인 판매의 거래조건 고지·청약철회 관련 규정과 현재 FAQ 환불 기준(학원법 인용)의 관계, 엣지영어에 어떤 법이 적용되는지
6. 개인정보: 수집 항목 고지, 해외 강사에게 정보 제공(국외 이전), 보관 기간, 미성년 학생 여부
7. 기존 학생에게 불리한 조건(예: SC1 변경권 4·6·10회 → 1·2·3회)을 새 판 동의로 바꿀 수 있는지
