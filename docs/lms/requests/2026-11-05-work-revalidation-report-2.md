## 2. 남은 배포 차단 오류

### R-20 — 저장 중 브라우저 뒤로 가기와 처리 결과 유실

1. 가상 학생 STU-0004의 취소 되돌리기 대상 change_requests 한 행만 트랜잭션으로 잠가 응답을 지연했습니다. 설정·스키마는 변경하지 않았습니다.
2. UI에서 실제 되돌리기를 클릭하고 “저장 중이에요…” 안내를 확인했습니다.
3. 브라우저 Back을 실행하자 native confirm 없이 Home으로 이동했습니다. 별도의 Home 링크 클릭 경로는 confirm이 나타났으므로 경로별 차이가 있습니다.
4. Home에 완료/실패 안내가 없었고 해당 변경은 여전히 applied였습니다. 요청의 DB 잠금 시간초과 가능성과 화면 이탈 자체의 인과는 구분합니다. **문제는 결과를 잃고 확인할 경로가 없는 것**입니다.
5. 잠금 트랜잭션은 종료됐고 QA 잠금 세션 0건을 확인했습니다. 이후 정상 UI 재시도와 되돌림으로 복구했습니다.

`src/app/lms/admin/useSavingGuard.ts`의 beforeunload/링크 클릭 방어만으로 History Back 경로가 보호되지 않습니다. 뒤로/앞으로/화면 이동 시 저장 처리 상태를 유지하고, 화면에 돌아오거나 재접속했을 때 서버 결과를 확인할 수 있어야 합니다.

R-06은 제품 오류 재현으로 단정하지 않지만, 다시 열기 실제 저장 확인이 배포 전 검증 과제로 남습니다.

## 5. 새로 확정하거나 추가한 오류

### R-02 — 다중 취소 부분 실패 후 화면 갱신 누락 (높음, 실제 재현으로 승격)

기존 보고서는 코드상 위험으로만 남겼지만 이번에는 실제 화면에서 재현했습니다.

1. STU-0004 학생 운영자 보기에서 11/10·11/12 12:30 KST 수업을 함께 선택.
2. 별도 관리자 수업변경 화면에서 11/12를 정상 취소.
3. 원래 화면의 ‘2회 취소하기’를 누르면 11/10 취소 성공 뒤 11/12 오류.
4. ‘1회 취소한 뒤 멈췄어요: 이미 처리된 수업입니다 (Student canceled in advance).’가 보이지만, 다음수업11/10·변경권1·보강0이 그대로.
5. 실제 DB는 두 수업 canceled, 현재 주기변경권0/다음주기1, applied취소 각1건.
6. 다시 누르면 첫 수업부터 이미 처리됨 오류. 새로고침하면 보강2·변경권0이 반영.

원인: `StudentHome.tsx` confirmCancelMany가 부분 성공 후 throw, 공통 run의 catch는 `actions.reload()`를 호출하지 않음. 재시도는 새 요청ID이지만 DB의 scheduled 검사로 중복 적용 차단.

**수정:** 실패 때도 서버 결과 재조회, 성공/실패 항목 분리, 미처리만 재시도. 재조회도 실패하면 확인필요 상태와 재조회 버튼 제공. 완료 문구 R-01·주기별 미리보기 R-12와 함께 검증.

### R-17 — 전부 불가 요청의 휴무 화면 상태 불일치 (보통)

이전 후속 실행에서 여러 후보 전부 불가인 동일 신청이 신청상세에는 재조율, 휴무안내에는 ‘강사 확인 중’으로 나타났습니다. 요청 상태를 화면마다 다시 추정하지 말고 동일한 전부불가/재조율 판정으로 표시해야 합니다. 실제 제안 여부를 잘못 표현하는 R-11도 함께 수정합니다.

### R-18 — 이관된 휴무 보강 확정 시 종료일 자동연장 누락 (높음)

- 이전 실제 실행: STU-0003 이관권 `fd4a98ab-c6a4-40d9-844d-20a47bf6421e`, tutor_leave=true, 원래12/7. 두 후보 불가 후 12/10 14:00 KST로 재조율 확정했지만 최종 종료는11/30에 머묾.
- 신청 `47e6523b-b2de-497f-920e-53e2564bf5a1`, 수업 `252dde61-db54-43b0-8d49-d139d9075d66`. 이번에는 감사이력 #2701/2703 및 현재 canceled/voided 복구 상태를 재확인.
- 코드·DB 원인: `admin_makeup_confirm`는 lessons에 migrated_makeup을 INSERT한 **뒤** migrated_items.lesson_id를 연결. lessons의 AFTER INSERT 연장 트리거는 연결 전 실행되어 해당 이관권을 찾지 못함. migrated_items에는 audit/no_delete 트리거만 있고 연결 후 연장재계산 없음.
- **수정:** 이관권 연결 완료 후 같은 트랜잭션에서 자동연장 재계산. 취소/삭제/재확정 시 회수와 다음수강권 충돌도 같은 최종종료일 기준으로 검증. 기존 수업·기존 수강권을 일괄 변경하지 않기.
- 기존 정상 신규휴무 보강 연장 통과는 유지. 이관 경로만 따로 실패 판정.

### R-19 — 보상수업 완료 시 Paid Y 표시 (높음)

- 이전 실행: 가상 보상수업에 완료 상태를 넣자 Class Record Paid Y 표시, 이후 scheduled로 원복.

- **수정:** 보상수업의 무급 규칙을 Paid 표시와 향후 정산 산식에 일치시키고 정규/보강/보상에 대해 검증. 실제 급여가 지급됐다는 뜻은 아님.

### R-20 — 관리자 저장 중 이동 시 처리 결과를 잃음 (보통)

- 시험 변경 기록 한 행의 처리 응답을 지연시킨 상태에서 되돌리기 저장 클릭. 버튼 disabled 확인 후 상단 Home 링크로 이동이 가능하고 경고 없음.

- DB의 기존8초 제한과 의도적 지연이 있어 **화면 이탈이 서버 실패를 유발했다는 인과관계는 입증하지 않음**.
- **수정:** 저장중 이동 제어 또는 완료상태가 유지되는 업무 알림, 복귀시 서버 재조회/재시도. 연결된 다른 요청까지 무조건 취소하는 방식은 피하기.
- 실제 인터넷 차단/응답유실을 주입한 시험은 아님.

### R-21 — 12주 범위 밖 날짜의 제한 사유가 잘못 안내됨 (낮음~보통)

이전 실행에서 마지막 허용일의 추가개방/철회는 저장됐으나 범위 밖 날짜는 ‘닫힌 시간이 없다’고 안내했습니다. 12주 제한을 명시하고 저장 거절 사유와 화면 문구를 일치시켜야 합니다.

## 4. 새로 확인한 오류와 위험

### R-01 여러 수업 취소 완료 문구가 실제 변경권 차감을 0개로 안내

- **중요도:** 보통. 변경권 관련 잘못된 안내이므로 배포 전에 수정·재검증 필요.
- **화면:** 학생 LMS 및 해당 운영자 보기 → 여러 수업 취소 → 완료 알림.
- **확인 방법:** 기준 커밋 코드 검토와 실제 클릭·저장·새로고침. STU-0004의 11/12·11/17 수업 두 건을 취소하자 완료 알림이 `변경권 0개 사용`이었지만 시험 DB의 미래 주기 변경권 장부에는 각각 −1, 총 2개 차감이 기록됐습니다. 원본 두 수업과 변경권은 운영진 되돌리기로 복구했습니다.
- **위치:** src/app/lms/student/StudentHome.tsx, confirmCancelMany 275~294줄 및 run 248~261줄.
- **원인:** credits와 makeups가 0인 상태에서 run의 두 번째 인자 문자열을 먼저 계산합니다. 비동기 취소가 끝나 해당 변수가 증가해도 이미 만든 성공 문구는 바뀌지 않습니다.
- **기대:** 2개 차감됐다면 ‘변경권 2개 사용’, 새 보강 권리가 2개 생겼다면 해당 안내 표시.
- **실제 결과:** 정상 취소 뒤 `변경권 0개 사용`으로 표시되고 보강 신청 안내도 빠집니다. DB에서는 해당 수업 주기의 변경권 2개가 정상 차감됐습니다. R-12의 잘못된 사전 미리보기와 결합되면 사용자가 결과를 예측할 수 없습니다.
- **클릭 재현 절차:** 가상 학생에 변경권 2개와 변경권 사용 조건에 해당하는 미래 수업 2개 준비 → 둘 다 선택 → 취소 전 안내 확인 → 취소 저장 → 완료 알림·변경권 잔여·보강 권리 비교 → 새로고침.
- **수정 지시:** 성공 문구를 작업 완료 뒤 확정된 결과로 만들도록 변경하세요. run에 결과 콜백을 받거나 취소 결과를 반환하게 하고, 서버 결과의 실제 차감 수·보강 권리 수를 사용하세요. 미리보기 예상치와 저장 결과를 혼용하지 마세요.

문구 수정 형식: `변경권 0개 사용` → `변경권 {실제 차감 수}개 사용 · 남은 변경권 {저장 후 잔여}개` → 실제 처리 결과와 일치하고 재문의·중복 처리를 줄이기 위해 필요합니다.

### R-02 다중 취소 중간 실패 후 이미 처리한 결과가 화면에 갱신되지 않는 경로

- **중요도:** 높음 가능성. **코드상 위험이며 실제 장애 재현 전까지 확정된 클릭 오류로 세지 않습니다.**
- **화면:** 같은 다중 취소 흐름.
- **확인 방법:** 코드 검토.
- **근거:** 수업별 취소를 순서대로 실행합니다. 한 건 성공 후 다음 건이 실패하면 ‘1회 취소한 뒤 멈췄어요’ 오류를 던집니다. 공통 run의 catch에서는 actions.reload를 호출하지 않습니다. 앞서 성공한 취소가 DB에 남아도 화면은 이전 수업·변경권 상태를 계속 가질 수 있습니다.
- **필요 재현:** 첫 건 성공, 두 번째 건만 충돌 또는 요청 실패가 나도록 가상 조건 구성 → 부분 성공 안내·목록·잔여권 확인 → 재시도 시 완료된 수업 중복 처리 여부 확인.
- **수정 지시:** 부분 성공에서도 저장된 상태를 다시 읽으세요. 성공·실패 수업을 구분하고 미처리 수업만 재시도하도록 하세요. 재조회까지 실패하면 전체 성공으로 표시하지 말고 현재 결과를 확인할 경로를 제공하세요.

### R-03 끝나는 시각의 휴무가 다음 날에 0분짜리 휴무로 표시됨

- **중요도:** 보통. 휴무가 이미 끝난 날에도 ‘Leave’가 보이므로 강사가 가능한 시간으로 착각하거나 반대로 하루 전체를 휴무로 오해할 수 있습니다.
- **화면·실제 클릭:** Alex → Schedule → Month → Sydney Time → 11월 5일. 달력에 Leave가 표시되고 날짜 상세의 휴무 버튼이 `Leave 02:00–Thu, Nov 5 02:00 Sydney Time`으로 나옵니다. 버튼을 누르면 `This time is in your leave.` 안내가 뜹니다. 새로고침 후 다시 확인해도 같았습니다.
- **기대:** 11월 4일 02:00부터 11월 5일 02:00까지인 휴무는 11월 5일 02:00에 끝납니다. 11월 5일에 0분짜리 휴무 일정이 나타나서는 안 됩니다.
- **교차 확인:** 시험 DB의 해당 `tutor_time_off` 시작 2026-11-04 02:00 Sydney, 종료 2026-11-05 02:00 Sydney. 종료 시각이 다음 날짜 시작/끝 처리에 잘못 포함된 것으로 보이나 정확한 코드 원인은 아직 추적하지 않았습니다.
- **확인 방법:** 실제 강사 화면 클릭·새로고침 + 시험 DB 읽기.
- **수정 지시:** 휴무를 날짜별로 나눌 때 종료 시각을 반열린 구간 `[start, end)`으로 처리하고, 날짜별 교집합이 0분인 행은 숨기세요. 11월 4일 상세는 실제 시작·끝을 보여주고 11월 5일에는 0분 이벤트가 없어야 합니다. KST·Sydney 및 서머타임 날짜 경계를 함께 시험하세요.

문구 수정 형식: `Leave 02:00–Thu, Nov 5 02:00 Sydney Time` → 해당 날에 행 자체를 표시하지 않음 → 실제 휴무가 없는 날짜를 휴무처럼 보여 주지 않기 위해서입니다.

### R-05 확정된 대체강사의 수업 입장 링크가 실제 회의실로 연결되지 않음

- **중요도:** 높음. 이 상태가 실수업에 적용되면 학생이 정해진 수업 시간에 입장하지 못할 수 있습니다.

### R-09 같은 강사의 기존 휴무 기간 안에 중복 휴무가 경고 없이 등록됨

- **중요도:** 보통. 중복 휴무가 업무 카드·안내·자동 연장 산식에 미치는 영향은 확인하지 못했으므로 실제 수업 사고로 단정하지 않습니다.
- **실제 재현:** 관리자 강사 휴무 목록에 Alex `11/23~11/30`이 이미 있음 → `+ 새 휴무 입력` → 같은 Alex의 `11/26~11/26`, 시험 사유 입력 → 미리보기 `걸리는 수업 0회·학생 0명` → 저장. 목록이 6→7로 늘고 같은 기간 안의 중복 휴무가 새로 생겼습니다. 곧바로 철회 사유를 입력해 철회했고 목록은 6으로 돌아왔습니다.
- **기대:** 포함되거나 겹치는 휴무가 있으면 기존 휴무 기간을 보여 주며 중복 저장을 막거나, 서로 다른 사유로 중복 등록이 필요한 정책이라면 영향과 중복 계산을 명확하게 안내해야 합니다.
- **확인 방법:** 실제 운영진 화면 가상 데이터 저장·철회. 수업 0회인 날짜였으므로 자동 연장 중복 여부는 미검증입니다.
- **수정 지시:** 동일 강사 휴무의 날짜 겹침을 저장 전에 검사하고 기존 휴무와 겹치는 구간·영향 학생을 보여 주세요. 중복 허용 정책을 확인한 뒤 허용한다면 학생·수업·자동 연장·업무 카드가 중복 생성되지 않는 회귀 시험을 추가하세요.

### R-10 이미 강사와 수업이 배정된 카드의 `수업 컨펌 완료`가 새 시간 선택으로 이어짐

- **중요도:** 높음. 기존 수업을 확인하려다 다른 시간의 새 배정 절차로 들어가므로 운영 업무가 끊기고 오조작 위험이 있습니다.
- **실제 재현:** 관리자 홈 `신규 매칭 · 기한 초과` 장하은(STU-0002) 카드에는 `강사 배정 ✓`와 `수업 컨펌 완료`가 함께 있음 → `수업 컨펌 완료` 클릭 → `강사·시간 고르기` 화면, Blair 선택 → `2. 시간 0/2`로 새 슬롯 2개를 고르라고 함. 기존 장하은 화·수 09:30 KST 정규 수업 칸은 `정규 수업`으로 비활성화되어 있고 기존 배정 선택을 완료하는 버튼은 보이지 않았습니다. 새 시간은 저장하지 않았습니다.
- **기대:** 이미 배정된 강사·요일·시각과 학생에게 확인해야 할 내용을 보여 주고, 그 확인 상태를 실제 저장해야 합니다. 기존 시간을 바꾸려는 경우에는 별도 일정 변경 절차를 명확히 구분해야 합니다.
- **확인 방법:** 관리자 카드 클릭→기존 강사 선택→시간표 실제 화면 확인. 최종 확정 저장은 하지 않았으므로 다른 경로에 완료 버튼이 있을 가능성은 배제하지 않습니다.
- **수정 지시:** 해당 카드의 대상 enrollment가 이미 강사·정규 수업을 가졌으면 현재 배정을 불러오는 확인 화면으로 연결하세요. `수업 컨펌 완료`를 기록할 서버 저장과 카드 갱신을 검증하고, 새 배정·일정 변경과 혼동되지 않게 버튼 이름과 다음 행동을 맞추세요.

### R-11 강사가 대체 시간을 제안하지 않았는데 제안한 것처럼 안내

- **중요도:** 보통. 학생과 운영진이 실제 답변을 잘못 이해할 수 있습니다.
- **실제 재현:** 운영진 STU-0003의 12/7 휴무 수업 보강 후보 12/8 14:00 KST를 신청 → Alex 운영자 보기 Home `Make-up requests`에서 후보 체크 없이 `QA test: I am not available at this time.` 메모로 `Send answer` 저장 → 학생 홈 목록 `강사님이 다른 일정을 요청했어요`, 상세는 `다른 일정 조율 중` → 관리자 수업 변경 화면 `아래에 강사가 말한 시간을 넣어 확정해 주세요` 표시. 강사는 다른 시각을 제안하지 않았습니다. 후보 확정 버튼은 불가 답변으로 비활성화되어 핵심 상태 전환은 정상입니다.
- **확인 방법:** 시험용 운영진·강사 운영자 보기·학생 운영자 보기 실제 클릭·저장·새로고침. 강사 본인 로그인에서 같은 조합은 미검증.
- **현재 문구 → 추천 문구 → 이유:** `강사님이 다른 일정을 요청했어요` → `강사님이 신청한 시간에는 어렵다고 답했어요` → 대체 시간 제안 여부를 단정하지 않기 위해서입니다. `강사가 말한 시간을 넣어` → `강사에게 다시 확인한 시간을 넣어` → 실제로 말하지 않은 시간을 적지 않게 하기 위해서입니다.
- **수정 지시:** 후보 전부 불가와 `Other times`의 구체적인 시간 제안 유무를 구분해 학생·운영진 문구를 나누세요. 강사 메모 자유문장을 자동으로 확정된 시간 제안으로 간주하지 마세요.

### R-12 다중 취소 미리보기가 미래 수업의 변경권 주기 대신 현재 주기를 사용

- **중요도:** 높음, 배포 전 수정 필요. 수업 취소와 보강권 유무가 확인 화면과 달라 실제 학생의 수업 계획에 영향을 줍니다.
- **실제 재현:** STU-0004 학생 운영자 보기에서 11/12·11/17 12:30 KST 정규 수업을 함께 선택. 11/5 현재 주기 10/14~11/10 변경권은 1개, 두 수업이 속한 11/11~12/8 주기는 2개. 미리보기는 `2회 · 변경권 1개 사용 · 잔여 0개`, 11/17은 `변경권 없음 · 1회 차감 · 보강 없음`, 남은 수업 `17→16`이라고 안내. 실제 취소 후 두 건 모두 보강 신청 권리가 생기고 남은 수업은 17회, 변경권은 미래 주기에서 −1씩 2개 차감됐습니다. 현재 주기 표시 1개는 그대로여서 새로고침 후에도 미리보기와 어긋납니다.
- **DB 대조:** `change_requests` 두 건은 `credits_left: 2→1→0`, `makeup_allowed: true`이며 `credit_ledger`는 11/11~12/8 기간에 −1 두 건. 두 수업은 운영진 화면에서 사유를 적어 되돌렸고, `scheduled` 및 미래 주기 변경권 2개 복구 확인. 감사 이력은 남았습니다.
- **확인 방법:** 실제 선택·저장·새로고침과 시험 DB 읽기 전용 대조. 강사 본인 세션 및 학생 본인 계정 로그인은 이 표본에서 미검증.
- **수정 지시:** 여러 날짜의 수업을 고를 때 **각 수업이 속한 28일 주기의 변경권 잔여**로 순차 미리보기를 계산하세요. 서로 다른 주기에 걸친 두 수업도 시험하고, 서버의 실제 적용 결과와 사전 안내의 보강권·남은 회차·주기별 잔여를 일치시키세요. R-01 완료 문구도 실제 결과로 생성하세요.

### R-13 가능 시간을 열어도 Home 보강 요청의 불가 상태가 갱신되지 않음

- **중요도:** 높음. 강사 응답 흐름이 막히므로 배포 전 수정 필요.
- **화면:** 운영자 보기 Alex → Home / Schedule / Make-up requests.
- **실제 재현:** STU-0003의 11/13 14:00 KST(16:00 Sydney) 50분 보강 요청은 닫힌 시간이어서 후보 비활성화. Schedule Week에서 해당 16:00 시작 칸을 Make available로 저장, request waiting으로 바뀐 것 확인 → Home → Make-up requests를 다시 열면 여전히 비활성화 및 `You have another class or time off then`. 같은 시각 DB는 available=true, conflict=null. 브라우저 새로고침 후 같은 요청을 열면 선택 가능해지고 Send answer 저장도 성공.
- **기대/실제:** 저장한 가능 시간과 후보 상태가 바로 일치해야 하나, Home은 이전 판정을 유지합니다.
- **수정 지시:** Schedule·Availability 저장 성공 후 상위 강사 화면의 요청·충돌 자료도 재조회하거나 관련 캐시를 무효화하세요. `TutorSchedule`은 자체 load만 호출하고 `TutorHome` 보강 목록을 갱신하는 콜백이 없는 부분을 점검하세요. 닫기→열기와 열기→닫기 양방향을 시험하세요.
- **확인 방법:** 실제 클릭·저장·화면 간 이동·새로고침 + 읽기 전용 DB + 코드 검토. 운영자 보기 표본이며 일반 강사 세션은 별도입니다.
- **별도 관찰:** Mia 최초 진입의 available/새로고침 후 not available 차이도 관찰했으나, 로딩 중 임시 표시와 영구 stale 상태를 분리하지 못했으므로 독립 결함 수에는 추가하지 않았습니다.

### R-14 휴무 보강 안내에 도시와 KST 기준 누락

- **중요도:** 보통. 시간 오인 방지를 위해 배포 전 문구 수정 권장.
- **화면/재현:** 가상 Blair 11/10~16 휴무 → STU-0002 11/10 `대체 강사 없음 → 보강` → 학생 안내의 `보냄` 기록 → 복귀 뒤 보강 날짜 잡기. 출력된 학생 문구는 `모두 평소 시간 오전 11시 30분 (현지 시간) - 11/17(화)`. 선택 체크박스는 `11/17(화) 09:30`이며 그 줄에 시간대가 없습니다.
- **기대/실제:** 학생은 Melbourne 기준 11:30, 운영진 후보는 KST09:30로 계산 자체는 맞지만 누구의 현지 시간인지 문구에 없고 두 시각의 연결도 빠져 있습니다.
- **현재 → 추천 → 이유:** `오전 11시 30분 (현지 시간)` → `11/17(화) 11:30 Melbourne 시간 · 한국 09:30` → 운영진 복사·전달 시 시간 기준 혼동 방지. 후보 체크박스도 `11/17(화) 09:30 KST`처럼 표기하세요. 학생의 다른 도시·날짜 변경 예시로 함께 확인하세요.
- **확인 방법:** 실제 화면 클릭 및 표시 문구 대조. 휴무는 시험 후 철회했으므로 같은 가상 조건으로 재현해야 합니다.

### R-15 정규 일정 변경 건수에 실제로 바뀌지 않은 수업 포함

- **중요도:** 보통. 배포 전 수정 권장.
- **화면/재현:** 운영진 학생 STU-0002 → 정규 일정 수정 → 화요일만 09:30→10:00, 수요일09:30 유지 → 미리보기·저장 → 안내문.
- **기대:** 변경1회, 유지1회. 실제 수업 두 건은 11/10 09:30→10:00, 11/11 09:30→09:30입니다.
- **실제:** 미리보기 `바뀌는 수업 2회`, 버튼 `2회 바꾸고 저장`, 저장 후 `바뀐 수업 2회 · 그대로0회`, 학생·강사 안내에도 두 건 모두 Changed classes로 포함됩니다. 날짜/시간 저장과 학생 화면 반영은 정상입니다.
- **수정 지시:** 변경 전후 시작·끝·담당 강사 등 실제 변경값을 비교해 unchanged를 분리하세요. 미리보기, 저장 결과, 변경 이력, 복사 안내문이 동일한 변경 목록을 사용하게 하세요. `2회 바꾸고 저장` → `1회 바꾸고 저장 · 1회 유지`.
- **확인 방법:** 실제 저장·새로고침·학생 운영자 보기. 다시 화요일09:30으로 복구했고 두 저장 이력과 미발송 안내가 남습니다.

### R-16 이미 답한 보강을 Schedule에서 다시 답하라고 안내

- **중요도:** 보통. 제한 정책을 바꾸지 말고 상태·안내 수정 필요.
- **화면/재현:** R-13 후보를 개방한 뒤 Alex가 가능 답 Send answer 저장, `Sent ✓ · Edge English will confirm` 확인 → Schedule Week 11/13 16:00 클릭.

- **기대/수정 지시:** 미응답과 운영진 최종 확정 대기를 구분하세요. 이 상태의 시간 수정이 정책상 금지라면 `Your answer has been sent. Waiting for Edge English to confirm.` 및 운영진 문의 경로를 제시하고, 추가 개방 행에도 잠금 사유를 표시하세요. 허용 여부를 임의 변경하거나 이미 답한 수업을 자동 취소하지 마세요.
