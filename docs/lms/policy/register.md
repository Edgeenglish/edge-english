# 운영정책 기준표 (Policy Register)

엣지영어 운영정책의 **유일한 기준 문서**. 계약서·FAQ·안내문·시트·LMS 코드는 모두 이 표를 따라야 하며, 서로 다르면 이 표에서 먼저 정리한다.
정책을 바꾸는 절차는 [`process.md`](process.md), 근거 문서 ID는 [`sources.md`](sources.md), 충돌 상세는 [`conflicts.md`](conflicts.md).

## 읽는 법

- **상태**: `확정`(근거 문서끼리 일치하고 실제 적용 중, 또는 대표가 정책 원본에서 확정) · `검토 중`(문서끼리 다르거나 규칙이 없음 → 결정 필요) · `변경 제안`(새로 제안, 승인 전) · `폐지`(더는 쓰지 않음, 기록용으로 남김)
- **대표 승인**: `✅ 승인`(날짜) · `◐ 대화 지시`(2026-10-16 대화에서 대표가 직접 말한 내용) · `◐ 기획서 결정 목록`(2026-10-11 기획서에서 체크된 항목) · `⬜ 미승인`. **◐는 정식 승인이 아니다.** R-0(확정 정책 일괄 승인)은 여전히 보류이지만, 2026-10-16 대표가 **공식 정책 원본(Google Docs, `sources.md` SRC-POLICY-V1)** 에 개별 조항을 직접 확정했다. 그 조항은 `✅ 승인 (2026-10-16, 정책 원본 A01…)`으로 표시한다. 원본에서 [개발요구]는 `✅ 승인 (… B01 개발요구)`, [추가확인]·[보류]는 `검토 중`으로 둔다.
- **정책 원본과의 관계**: 정책 결정의 원본은 Google Docs(대표 관리), 이 표는 개발용 사본이다. 둘이 다르면 Google Docs가 맞고 이 표를 고친다. 실제 운영 데이터(학생·수업·결제)의 원본은 Supabase다. 대조표: [`official-source.md`](official-source.md)
- **핵심 영향 · 적용 대상 · 판본 차이**: 수강 횟수·변경권·보강·이월·장기 연기·강사 급여·환불에 직접 영향을 주는 정책에만 있음. `상태: 확정`이어도 **적용 대상에 적힌 판본에만 확정**이고, 다른 판본 학생·강사에게는 '판본 차이'의 조건이 적용될 수 있다. 판본 코드는 `sources.md`.
- **기존/신규**: 계약서 9조에 따라 학생은 서명한 계약서 판본이 재등록 후에도 유지될 수 있다(수정 계약서를 받으면 새 판 적용). 그래서 판본별로 다를 수 있는 규칙은 따로 적는다.
  - 학생 계약 판본: `SC0A`(2024-09 이전, 12시간 기준) · `SC0B`(2024-11, 30일·효력 조항 없음) · `SC0C`(2025-05, 30일) · `SC1`(2025-10~12, 30일) · `SC2`(2026-01~, 28일) · `SC3`(2026-10 초안)
  - 강사 계약 판본: `TC0`(2024-08 국내, 원화 시급) · `TC0B`(2025-11-04, $14+최대 $2) · `TC1`(2025-11-27, $14+최대 $3) · `TC2`(2026-01, $11) · `TC3`(2026-08, $11)
- **안내서만 받은 학생 (2026-10-16 추가)**: 2026년 초 어느 시점부터 학생에게 계약서를 보내지 않고 필독안내서(이미지 2장)만 전달했다(POL-OP-09). 이 학생들에게는 **계약 판본이 없다.** 이 표에서 '적용 대상: SC2 이후' 같은 판본 조건은 계약서를 받은 학생에게만 해당하고, 안내서만 받은 학생에게 어떤 규칙이 적용되는지는 **정하지 않았다**(POL-OP-10·11, 법률 미확인). 계약서가 없는 학생에게 SC2 등 계약 판본을 임의로 넣지 않는다.
- **고칠 곳**: 이 정책이 바뀌면 함께 고쳐야 하는 곳. `code:` 는 LMS 코드, `test:` 는 자동 테스트.
- 이 표의 `### POL-…` 제목과 `- **상태**:` 줄은 자동 테스트가 읽으므로 형식을 바꾸지 않는다 (`src/lms/rules/policy-register.test.ts`).

마지막 전체 확인: **2026-10-17** (정책 원본 v1.0 최우선 장기 목표·A01~A32·H01~H11 대조)

## 수강기간 (PER)

### POL-PER-01 · 수강 단위
- **현재 규칙**: 신규 판매는 4주 / 12주 / 24주. 화면에는 "1개월 = 4주 기준" 표기.
- **근거**: SRC-PRICE, SRC-FAQ(2026-10-12~), SRC-PDF, SRC-SC2
- **상태**: 확정
- **대표 승인**: ◐ 대화 지시 (2026-10-16) — 정식 승인 아님
- **핵심 영향**: 수강 횟수
- **적용 대상**: 신규 등록 (현행 상품)
- **판본 차이**: 옛 상품(1개월=30일, 3개월="120일", 2개월, 2024 판)은 원래 조건으로 이관
- **적용 시작**: 홈페이지는 2026-10-10~12 주 단위로 변경
- **기존/신규 차이**: 과거에는 1개월(30일)·3개월(SC1은 "120일")·2개월(이벤트, 마감) 단위 판매 이력. Master Sheet에 8주 학생 존재. → 기존 등록은 **원래 날짜 그대로 이관**하고 다시 계산하지 않는다.
- **충돌**: CF-04
- **고칠 곳**: code `CONFIRMED.courseWeeks` (policy.ts), DB `enrollments.weeks`, 수업료 페이지 탭 이름('개월' 표기), FAQ '수강권 사용 기한'
- **마지막 확인**: 2026-10-16

### POL-PER-02 · 기간 길이 (28일, 시작일 포함)
- **현재 규칙**: 1기간 = 시작일 포함 28일 (종료일 = 시작일 + 27). 12주 = 3기간, 24주 = 6기간, 끊김 없이 이어짐.
- **근거**: SRC-SC2, SRC-FAQ, SRC-TGUIDE, SRC-PDF, SRC-MASTER 수식
- **상태**: 확정
- **대표 승인**: ◐ 대화 지시 (2026-10-16) — 정식 승인 아님
- **핵심 영향**: 수강 횟수
- **적용 대상**: SC2 이후 계약
- **판본 차이**: SC0B·SC0C·SC1은 "한 달 30일", SC0A는 "4주"
- **적용 시작**: SC2 (2026-01 서명본에서 확인)
- **기존/신규 차이**: SC1 학생은 "한 달 30일" 기준으로 계약 (CF-04)
- **충돌**: CF-04, CF-11
- **고칠 곳**: code `computePeriods` (period.ts), test '수강기간 계산', DB `enrollments`·`enrollment_periods` 검사, 계약서 2조, FAQ
- **마지막 확인**: 2026-10-16

### POL-PER-03 · 최초 수강 시작일
- **현재 규칙**: 첫 정규 수업일. 주말·공휴일에 시작해도 같은 계산.
- **근거**: 대표 지시(2026-10-16), SRC-PDF, SRC-MASTER '수강기간 시작일'
- **상태**: 확정
- **대표 승인**: ◐ 대화 지시 (2026-10-16) — 정식 승인 아님
- **기존/신규 차이**: 없음
- **충돌**: 없음
- **고칠 곳**: code `generateRegularLessons` 시작일 검사, test '시작일이 수업 요일이 아니면 거부'
- **마지막 확인**: 2026-10-16

### POL-PER-04 · 24주(6기간) 계산
- **현재 규칙**: 24주 = 28일 × 6기간.
- **근거**: SRC-PDF, SRC-FAQ(2026-10-12 이전 문구에도 "24주 안에"), SRC-PRICE
- **상태**: 확정
- **대표 승인**: ◐ 대화 지시 (2026-10-16) — 정식 승인 아님
- **핵심 영향**: 수강 횟수
- **적용 대상**: 24주 상품
- **판본 차이**: 어느 계약서에도 24주 기간 정의가 없음 (FAQ·PDF·수업료 페이지만)
- **기존/신규 차이**: Master Sheet는 3기간까지만 계산 (버그). SC3 초안은 6개월 기간이 빈칸.
- **충돌**: CF-11
- **고칠 곳**: code `computePeriods`, test '24주 = 28일 × 6기간', SC3 빈칸, FAQ '(4주~12주)' 문구
- **마지막 확인**: 2026-10-16

### POL-PER-05 · 수강권 사용 기한
- **현재 규칙**: 등록한 수업은 수강 기간 안에 사용. 종료 후 남은 수업은 소멸 (이월 예외는 POL-RN-01).
- **근거**: SRC-SC1·SC2, SRC-FAQ, SRC-GUIDE, SRC-TGUIDE
- **상태**: 확정
- **대표 승인**: ⬜ 미승인
- **핵심 영향**: 수강 횟수
- **적용 대상**: SC0B 이후 전 판본
- **판본 차이**: SC0A는 소멸 문구 대신 "보강은 취소일로부터 2주 안"
- **충돌**: 없음
- **고칠 곳**: 학생 화면 문구, 재등록 안내
- **마지막 확인**: 2026-10-16

### POL-PER-06 · 보강 기한
- **현재 규칙**: 최종 종료일(KST) 23:59까지 시작하는 수업.
- **근거**: SRC-PDF (정확한 시각). SRC-FAQ·SRC-GUIDE·SRC-SC2는 "수강권 유효기간 내"로만 표현
- **상태**: 확정
- **대표 승인**: ◐ 기획서 결정 목록 (2026-10-11) — 정식 승인 아님
- **핵심 영향**: 보강
- **적용 대상**: SC0B 이후
- **판본 차이**: SC0A는 "취소일로부터 2주 안"
- **충돌**: 없음 (표현 차이만)
- **고칠 곳**: code `isMakeupSlotAllowed`, test '보강 기한'
- **마지막 확인**: 2026-10-16

### POL-PER-07 · 강사 사유로 못 잡은 보강의 기간 연장
- **현재 규칙**: **규칙 없음.** 기간 끝 무렵 강사가 취소하면 학생이 보강을 잡을 시간이 없을 수 있음.
- **근거**: 없음 (빈칸)
- **상태**: 검토 중
- **대표 승인**: ⬜ (D-10)
- **고칠 곳**: 운영자 '기간 연장' 기능
- **정책 원본 메모**: 정책 원본 A19·A20은 '강사 장기 휴무' 연장 규칙이다. 기간 끝 무렵 강사 단건 취소로 보강을 못 잡는 경우에 같은 방식을 쓸지는 원본에 없음 → 검토 중 유지
- **마지막 확인**: 2026-10-16 (정책 원본 v1.0 대조)

- **충돌**: 없음

## 계정·인증 (AC)

### POL-AC-01 · 최우선 장기 목표: 공식 홈페이지 통합 시스템의 기반
- **현재 규칙**: 장기적으로 엣지영어 **공식 홈페이지**에서 학생이 회원가입·로그인·수강신청·결제·수업 일정·변경·보강·적립금 확인을 모두 하고, 강사·운영자도 같은 시스템에서 권한별로 일한다. 지금 만드는 LMS는 그 기반이며 나중에 버리거나 다시 만들지 않는다: **학생 고유 ID(`students.id`·`STU-`)와 계정 연결(`app_users`) 유지, 수업·수강권·보강·변경권·결제 확인·적립금 데이터 유지, 학생·강사·운영자 권한 분리, 외부 결제 ↔ 내부 수강등록의 정확한 연결.** 단, 현행 홈페이지·아임웹 결제·시트를 지금 교체하지 않으며, 큰 구조 변경·새 서비스·유료화·운영 환경 변경은 비교안과 영향 범위를 먼저 보고하고 승인받는다.
- **근거**: SRC-POLICY-V1 머리말 「최우선 장기 제품 목표」·H11
- **상태**: 확정

- **마지막 확인**: 2026-10-17

### POL-AC-02 · 1인 1계정 · 학생 1명 = 개인 이메일 1개

- **상태**: 확정

### POL-AC-03 · 계정 생성 방식: 운영자 초대 → 공개 회원가입 단계적 도입
- **현재 규칙**: **초기**에는 운영자가 학생별 개인 계정을 등록·초대하고 학생은 그 계정으로 로그인. 공개 회원가입은 열지 않음. **이후** 공식 홈페이지에 직접 회원가입을 추가하되, 기존 학생은 재가입·데이터 재입력 없이 기존 계정·학생 ID·기록을 그대로 사용. 외부 결제 데이터 자동 이전·PG 연동은 별도 작업·승인.
- **근거**: SRC-POLICY-V1 A30 (① 단계적 도입 선택)
- **상태**: 확정
- **대표 승인**: ✅ 승인 (2026-10-17, 정책 원본 A30)
- **고칠 곳**: Supabase Auth 회원가입 설정(시험·운영 모두 끔), 운영자 학생 등록 기능
- **마지막 확인**: 2026-10-17

### POL-AC-04 · 계정 ↔ 학생 연결은 검증된 매핑으로만
- **현재 규칙**: 로그인 계정과 학생 기록의 연결(`app_users`)은 **운영자 등록 또는 운영자가 확인한 절차로만** 만든다. **이메일이 같다는 이유만으로 자동 연결하지 않는다.** 회원가입(계정 생성)만으로는 수강생 권한이 생기지 않는다 — 장래 공개 가입도 '가입 → 수강신청·결제 확인 → 연결·수강권 활성화'를 별도 단계로. 연결되지 않은 계정은 학생·결제·수업 데이터를 볼 수 없다(RLS).
- **근거**: SRC-POLICY-V1 최우선 장기 목표·H11·A30
- **상태**: 확정
- **대표 승인**: ✅ 승인 (2026-10-17, 정책 원본 A30·H11)
- **고칠 곳**: DB RLS(`my_student_id`·`my_tutor_id`·`is_admin`), `authz-probe.sql` '미등록' 항목, 운영자 계정 연결 화면
- **마지막 확인**: 2026-10-17

### POL-AC-05 · 운영자 추가 인증 (TOTP)
- **현재 규칙**: 운영자는 이메일 6자리 코드 로그인에 더해 **무료 인증 앱 TOTP**(처음 QR 등록, 이후 새 로그인 때 6자리 코드)를 쓴다. 운영자 권한은 추가 인증을 마친 세션(Supabase `aal2`)에서만 DB가 인정한다(서버·RLS에서 강제, 화면만으로 막지 않음). 일상 사용이 번거롭지 않게 같은 기기에서는 세션을 유지. 세션 유지 기간·민감 작업 재확인·분실 대비 방식은 D-29.
- **근거**: SRC-POLICY-V1 A27, 대표 메시지(2026-10-17)
- **상태**: 확정
- **대표 승인**: ✅ 승인 (2026-10-17, 정책 원본 A27 대표요구)
- **고칠 곳**: DB `is_admin()`(aal2 확인 추가 예정), 운영자 로그인·TOTP 등록 화면, `authz-probe.sql`
- **마지막 확인**: 2026-10-17

### POL-AC-06 · 인증·알림 메일 발송 서비스
- **현재 규칙**: **정하지 않음.** Supabase 기본 메일은 팀 멤버 주소에만·시간당 약 2통이라 학생 운영에 쓸 수 없음 → 실제 학생 이메일 코드 시험 전 별도 SMTP(발송 서비스) 필요. 업체·비용·도메인 인증(DNS)·발송 범위는 대표 승인 사항. 지금은 가입·결제·실제 발송 하지 않음.
- **근거**: SRC-POLICY-V1 H10·A28
- **상태**: 검토 중
