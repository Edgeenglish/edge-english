# 정책 변경·충돌 점검 절차

목표: 같은 규칙이 계약서·FAQ·안내문·시트·LMS에 서로 다르게 적히는 일을 막는다.
처음에는 **문서 3개(기준표·근거 목록·충돌 목록) + 체크리스트 + 자동 테스트 1개**로 시작한다. 별도 정책관리 시스템은 만들지 않는다.

## 1. 원칙

1. **기준표가 먼저, 문서는 나중.** 규칙을 바꿀 때는 `register.md`를 먼저 고치고, 계약서·FAQ·안내문·코드는 기준표를 따라 고친다.
2. **승인은 대표만.** Claude는 비교·영향 분석·초안 작성까지. 상태를 `확정`으로 바꾸거나 `대표 승인 ✅`을 적는 것은 대표 결정 후.
3. **미확정 규칙은 코드에 기본값으로 넣지 않는다.** 값이 없으면 기능이 동작하지 않게 막는다(`PendingPolicy`).
4. **지우지 않는다.** 바뀐 규칙은 `폐지`로 표시하고 남긴다. 근거 문서 버전도 추가만 한다. git 기록이 전체 이력.
5. **판본별 적용.** 학생은 서명한 수강계약서 판본, 강사는 서명한 강사계약서 판본을 따른다. 새 규칙은 "언제부터, 누구에게"를 반드시 적는다.

### 문서가 서로 다를 때 판단 순서 (자동 결정 아님 — 판단 재료)

| 확인할 것 | 질문 |
|---|---|
| 계약 효력 | 그 사람이 서명(결제로 동의)한 판본에는 뭐라고 적혀 있나? 새 계약서를 받았나? |
| 대외 안내 | 학생·강사가 실제로 본 안내(FAQ·안내서·가이드)는 뭐라고 했나? 언제부터? |
| 실제 운영 | 지금까지 실제로 어떻게 처리해 왔나? (시트·카톡 기록) |
| 유불리 | 안내가 계약보다 학생·강사에게 유리한가, 불리한가? (불리하게 바꾸는 것은 새 판본부터) |
| 날짜 | 규칙이 바뀐 날짜와 그 사람의 등록·계약 날짜 중 어느 것이 먼저인가? |

## 2. 정책 변경 절차 (6단계)

```
① 제안 발생 → ② 기존 정책과 비교 → ③ 충돌·영향 분석 → ④ 대표 승인 → ⑤ 기준표 갱신 → ⑥ 문서·LMS·테스트 반영
```

| 단계 | 누가 | 할 일 | 결과물 |
|---|---|---|---|
| ① 제안 | 대표 또는 Claude | "취소 기준을 6시간 → 12시간으로" 같은 제안. 새 문서(계약서 초안 등)를 받은 경우도 여기서 시작 | 기준표에 `변경 제안` 항목 추가 (기존 항목은 그대로) |
| ② 비교 | Claude | 같은 주제의 기존 정책 ID, 근거 문서 문구를 나란히 정리 | 비교표 |
| ③ 영향 | Claude | 아래 **영향 체크리스트**를 채움. 기존 학생·강사 적용 방법 제안 | 충돌 목록에 CF 항목 추가 또는 갱신 |
| ④ 승인 | 대표 | 적용 대상(신규만/전원), 시작일, 공지 방법 결정 | `07-decisions.md`에 기록 |
| ⑤ 기준표 | Claude | 새 규칙 `확정` + `대표 승인 ✅ 날짜`, 옛 규칙은 `폐지`(삭제 안 함) | register.md 갱신 |
| ⑥ 반영 | Claude (외부 공개는 대표 승인 후) | 체크리스트의 모든 곳 수정, 코드·테스트 수정, `npm test` 통과 확인 | 수정 목록 + 테스트 결과 |

### 영향 체크리스트 (정책 1개 바꿀 때마다 복사해서 사용)

```
정책: POL-___ (제목)          변경: (전) ___ → (후) ___
적용 대상: □ 신규 등록부터  □ 재등록부터  □ 전원   시작일: ____-__-__

학생에게 보이는 곳
 □ 수강계약서 (다음 판본)         □ 홈페이지 FAQ (항목 번호: __)
 □ 수업전 필독안내서              □ 홈페이지 공지·수업료·이벤트
 □ 등록 안내문(카톡)              □ LMS 학생 화면 문구·팝업

강사에게 보이는 곳
 □ 강사계약서 (다음 판본)         □ Regular Class guide
 □ Compensation & Incentive Policy □ Class Record 안내 줄
 □ LMS 강사 화면 문구

운영·시스템
 □ Master Sheet 상태매핑표·수식 (병행 운영 중이면)
 □ LMS 규칙 코드 (src/lms/rules/…)  □ LMS DB 제약 (supabase/…)
 □ 자동 테스트 (값·경계 사례)        □ 정산·알림 템플릿

기존 사람 처리
 □ 기존 학생 몇 명 해당? 판본별 적용 방법   □ 기존 강사 해당?
 □ 공지 필요 여부·방법

확인
 □ npm test / npm run test:db 통과   □ 대표 승인 기록 (07-decisions.md)
```

각 정책의 "고칠 곳"은 `register.md`에 미리 적어 두었으므로, 체크리스트를 채울 때 그 줄부터 본다.

## 3. 점검을 언제 하나

### A. 일이 생겼을 때 (Claude가 그 자리에서 실행 — 예약 불필요)

| 계기 | 점검 |
|---|---|
| 대표가 새 문서·수정본을 공유했을 때 (계약서, 가이드, FAQ 수정 등) | 문서 안의 규칙을 기준표와 한 줄씩 대조 → 다르면 CF 추가, `sources.md`에 버전 추가 |
| FAQ·공지·수업료 등 홈페이지 문구를 고칠 때 | 고친 문구가 기준표와 같은지 대조 (다르면 고치지 않고 먼저 보고) |
| LMS 규칙 코드를 고칠 때 | 자동 테스트가 기준표 상태를 검사 (아래 C) |
| 학생·강사에게 새 계약서를 보내기 전 | 초안이 기준표 `확정`과 같은지, 내부 메모·빈칸이 없는지 |
| 운영 중 새로운 경우가 생겼을 때 (예: 강사 장기 휴무) | 기준표에 규칙이 있는지 → 없으면 `검토 중`으로 추가하고 결정 요청 |

### B. 정기 점검 (예약 작업이 있어야 가능 — 지금은 만들지 않음)

| 점검 | 주기 | 하는 일 | 필요 조건 |
|---|---|---|---|
| 기준표 전체 재확인 | 분기 1회 | Drive의 최신 계약서·가이드와 기준표 대조, `마지막 확인` 날짜 갱신 | 예약된 Claude 작업 + Google Drive 읽기 권한 |
| 시트 ↔ LMS 숫자 대조 (병행 운영 기간) | 주 1회 | 학생별 남은 회차·변경권·종료일 비교 | LMS 시험 DB + 시트 읽기 |
| `검토 중` 항목 알림 | 월 1회 | 오래 미결인 항목을 대표에게 요약 | 예약 작업 |

추천: **병행 운영(3단계)을 시작할 때 주 1회 대조만 예약 작업으로 켜고**, 나머지는 문서가 바뀔 때 A로 충분하다. 예약 작업은 대표 승인 후 만든다.

### C. 자동 검사 (이미 만듦)

`src/lms/rules/policy-register.test.ts` — `npm test` 때마다 실행
- 코드가 참조하는 정책 ID가 기준표에 실제로 있는지
- 코드가 "확정 값"으로 쓰는 규칙이 기준표에서 `확정`인지
- 코드에서 운영자 결정을 기다리는 규칙(`PendingPolicy`)이 기준표에서 아직 `검토 중`/`변경 제안`인지 → 결정이 나면 테스트가 실패해서 코드를 갱신하라고 알려 줌
- 요약표 숫자가 실제 항목 수와 같은지
- 상태매핑표 14개가 TypeScript 규칙과 DB 기준값에서 같은지

## 4. 나중에 자동화할 가치가 있는 것 (판단 기준)

| 후보 | 지금 | 언제 할 가치가 있나 |
|---|---|---|
| FAQ 문구 안의 숫자(6시간, 변경권 개수 등)를 기준표와 자동 대조 | 안 함 | FAQ를 자주 고치게 되면. 만드는 데 반나절 정도 |
| 기준표를 DB 표로 옮겨 관리 화면에서 보기 | 안 함 | 정책이 100개를 넘거나 다른 사람이 함께 관리하게 되면 |
| 계약 판본별 규칙을 화면에서 선택 | 안 함 | 판본이 3개 이상 동시에 살아 있으면 (지금 SC1·SC2 확인 중) |

## 6. 검사 구현 현황 (2026-10-16)

세 가지 검사를 구분한다. ✅ 구현·테스트 통과 · ◐ 일부 · ❌ 미구현

| 미확정 규칙(`PendingPolicy`)이 기준표에서 아직 미확정인지 | ✅ | 결정되면 테스트가 실패해 코드 갱신을 알림 (실제로 실패하는 것 확인함) |

| 근거 문서(Drive 계약서·가이드)가 바뀐 것 감지 | ❌ | 문서를 다시 읽어야 알 수 있음 → 3장 A(일이 생길 때)·B(정기 점검) |

### B. 문서 간 실제 내용 충돌 검사

| 검사 | 상태 | 비고 |
|---|---|---|
| 계약서·FAQ·안내서·강사 가이드·급여정책·시트 대조 | ◐ **사람(Claude)이 읽고 대조** | 결과는 `conflicts.md` 22건. 자동 검사 아님 |
| 상태매핑표 TS ↔ DB | ✅ 자동 | 위 A |
| FAQ(`src/data/faqs.json`) 문구 ↔ 기준표 자동 대조 | ❌ | 만들 수 있음(예: FAQ의 "6시간", "1회/2회/3회", 이월 기한 문구를 기준표 값과 비교). 반나절 정도. 지금 돌리면 이월·장기 연기에서 실패하므로 결정(D-1a·D-3) 후 만드는 것이 의미 있음 |
| Drive 계약서·가이드 ↔ 기준표 자동 대조 | ❌ | 문서를 읽는 권한·예약 작업 필요. 판본 판별(`terms.ts`)은 그 첫 단계로 쓸 수 있음 |

### C. 학생·강사별 계약 판본 적용

| 검사 | 상태 | 비고 |
|---|---|---|
| DB에 학생 등록별 판본(`enrollments.terms_version`), 강사별 계약(`tutor_contracts`) 기록 | ✅ | DB 테스트로 학생·강사 판본 섞임 거부 확인 |
| 옛 판본 등록을 실제 날짜 그대로 이관 | ✅ | DB 테스트 |
| 계약서 본문으로 판본 판별 (`classifyContract`) | ✅ | 가짜 문구 테스트 14개, 이름·연락처는 결과에 안 남음 |
| 발송·동의·서명 기록으로 적용 판본 판정 (`assessTerms`) | ✅ | 가짜 사례 테스트 9개 (확인됨/추정/미확인, 결제가 발송보다 앞선 경우, 새 판본 미동의, 강사 1판 갱신 등) |
| 판정 코드의 판본 = DB 판본 목록 | ✅ | 자동 테스트 |
| **판본별로 다른 규칙 적용** (예: SC1 학생은 30일·변경권 4/6/10) | ❌ **의도적으로 미구현** | 지금 규칙 코드는 SC2 이후 기준만. SC1 등 옛 판본 규칙은 D-16 결정 후 추가 (정해지지 않은 규칙을 넣지 않기 위해) |
| 실제 학생·강사가 어느 판본인지 | ❌ | `contract-version-check.md` 절차로 확인 필요 (대표 확인 항목 포함) |
