# 20. 운영진 취소·변경·보강 시범 운영안 — 제안 (2026-10-26)

근거: handoff 2026-10-26 대표 결정(개발 순서 ① 유지, 운영진 기능 먼저 실사용, 평가 기준 = 카톡 취소 1건당 클릭 수·직접 확인할 정보 양), 정책 원본 H26(7)(입력일 ≠ 전환일), migration 1500·1600·1700, `/lms/admin/change`·`/lms/admin/students/import` 코드.
**숫자(시범 인원·기간·대조 주기)는 정하지 않았음 — 9절 질문.** 운영 DB 실제 입력·시트 운영 중단은 이 제안과 별도 승인.

## 1. 한 줄 요약
시범 학생의 **취소·변경 판정·안내·보강 확정은 LMS로, 시트는 지금처럼 원본으로 유지(병행)** → 건마다 시트와 대조 → 문제없으면 학생별 전환. 병행 기간에는 업무가 **줄지 않고 조금 늘어남**(LMS 처리 + 시트 기록). 줄어드는 건 전환 뒤부터.

## 2. 단계
| 단계 | 내용 | 승인 |
|---|---|---|
| 0 | C: 운영 DB에 1700 적용 + `lms-prod`에 수업 변경 화면 반영. 운영 DB 학생 0명이라 지금 데이터 영향 없음 | 오늘 요청 |
| 1 | 시범 강사·학생 운영 DB 입력 (3절 데이터) → 입력 직후 시트와 1회 대조(D-52 [대조 완료]) | 별도 승인 |
| 2 | 병행 운영: 시범 학생 카톡 취소 요청 → LMS에서 처리·안내 복사·발송 → **시트에도 지금처럼 기록** | 1과 같이 |
| 3 | 대조: 처리할 때마다 LMS 결과(취소한 날짜·변경권 잔여·보강 날짜)와 시트가 같은지 확인 | — |
| 4 | 전환 판단: 학생별 전환일(`lms_since`)부터 변경권·보강은 LMS만 (5절 위험 때문에 범위 질문 있음) | 별도 승인 |

## 3. 필요한 데이터
**강사 (운영 DB에 강사 등록 화면 없음)**
- 꼭 필요: 영문 이름(학생 안내·강사 안내에 그대로 나감), 나라, 시간대 — `tutors` 표에 이 3개만 필수
- 넣는 방법 제안: Claude가 이름·나라·시간대만 넣는 SQL을 복사 버튼 페이지로 → 대표가 운영 SQL Editor에서 1번 실행. 강사 수가 적어 화면 개발은 안 함(기준 ③)
- 선택: 휴무 날짜(`tutor_time_off`) — 입력 화면 없음(2순위 강사 휴가 단계에서). 안 넣으면 보강 확정 때 **강사 휴무 검사가 비어 있음** → 대표가 직접 확인
- 필요 없음: 이메일·Meet 주소·가능 시간(보강 확정은 가능 시간을 보지 않음 — 강사 답을 받고 확정하므로)

**학생 (D-52 기존 학생 입력 화면 그대로)**
- 시범 학생: 이름(한글·영문), 상품·주 횟수·수업 길이, 수강 시작일, 담당 강사·고정 요일·시각, 앞으로 남은 첫 정규 수업일, 지금 기간 남은 변경권, 미완료 보강(예약됨/미예약), 시트 남은 횟수 대조
- 이메일·전화·주소 등 개인정보는 넣지 않음 (입력 화면에도 없음)
- **같은 강사의 다른 학생 시간표**: 보강 확정 때 DB가 '그 강사의 다른 수업·휴식 10분'과 겹치는지 검사하는데, LMS에 없는 수업은 못 봄 → 선택지 (9절 ②)
  - 가. 시범 강사의 지금 학생 전원을 D-52로 입력(전환은 시범 학생만, 나머지는 시트 관리 그대로) — 검사 정확, 입력 시간 늘어남
  - 나. 시범 학생만 입력 — 입력 적음, 보강 확정할 때마다 대표가 시트로 강사 시간 겹침을 직접 확인

## 4. 남는 수동 처리 (시범 중)
1. 카톡·WhatsApp 요청 읽고 **어느 수업인지 판단** — 시스템이 해석하지 않음(대표 결정). 화면에는 실제 예정 수업 목록이 날짜·요일·시각으로 나와서 '다음 주 목요일'을 목록에서 고르기만 함
2. **요청 받은 시각 입력** — 기본값이 '지금'이라 바로 처리하면 그대로, 나중에 처리하면 카톡 받은 시각으로 고쳐야 함. 안 고치면 6시간 판정이 틀릴 수 있음 (화면이 막지 못함)
3. 안내 [복사] → 카톡·WhatsApp에 붙여 넣어 보내기 → [보냈어요] (자동 발송 없음)
4. 강사에게 보강 가능 시간 묻기 → 답 받으면 [확정]
5. 시트 기록(병행 기간): 학생 수강현황·변경권·보강, 그리고 **강사 Class Record**
6. 지난 수업 처리: 수업 완료 기록(Class Record)은 3순위라 **LMS에서 지난 수업은 계속 '예정' 상태로 남음** → LMS의 '남은 수업 수'를 그대로 믿을 수 없음. 대조는 '오늘 이후 예정 수업 수 + 미완료 보강'과 시트 남은 횟수로 (지난 수업은 시트 기준)
7. 강사 휴무 확인(휴무를 안 넣으면), 3절 '나'를 고르면 강사 시간 겹침 확인

## 5. 시트 이중 관리 위험
| 위험 | 생기는 일 | 막는 방법 |
|---|---|---|
| 한쪽만 기록 | LMS는 취소, 시트는 그대로(또는 반대) → 변경권 잔여·남은 횟수가 달라짐 | 병행 기간엔 '시트 기록까지 끝나야 처리 끝'. 대조를 건마다 |
| 강사 Class Record | 강사가 시트 Class Record에 취소 상태를 따로 적음 → LMS와 세 번째 기록. 강사가 LMS 안내 전 기록·잘못 기록할 수 있음 | 3순위(강사 직접 입력) 전까지는 Class Record를 원본으로 두고 LMS는 대조만. **누가 Class Record에 취소를 적는지 확인 필요** (9절 ④) |
| 되돌리기 누락 | LMS에서 [되돌리기]만 하고 시트는 그대로 | 되돌리기도 시트에 같이 |
| 적립금(강사 늦은 취소 2,000원) | LMS 적립금 표와 지금 적립금 기록 두 곳 | 시범 중에는 지금 기록 방식을 원본으로, LMS 적립금은 대조만. 결제 반영은 지금 방식 |
| 전환 뒤 착각 | 전환한 학생인데 시트를 고치거나, 안 한 학생인데 LMS만 봄 | 전환한 학생 시트 맨 위에 '○/○부터 변경권·보강은 LMS' 한 줄 (시트 자동 채우기는 만들지 않음 — 대표 결정) |
| 정규 수업이 지나도 '예정' | LMS 화면 숫자를 남은 횟수로 오해 | 4절 6번 대조 방법. 3순위 전까지 남은 횟수 원본은 시트 |

## 6. 되돌리기 방법
- **건 하나**: 변경 기록 [되돌리기] → 수업 '예정'으로, 변경권 +1, 적립금 회수, 그 취소로 잡은 보강은 무효. 안내를 이미 보냈으면 정정 안내만 생김(안 보냈으면 '보낼 필요 없음'). 이력은 남음
- **잘못 넣은 보강**: [잘못 넣은 보강 삭제]
- **학생 하나 시범 중단**: 시트가 원본이라 LMS 사용만 멈추면 됨. 운영 DB 기록은 지우지 않음(변경 이력은 설계상 못 지움). 전환일을 정했으면 비움
- **시범 전체 중단**: 위와 같음. 시트로만 계속. LMS 데이터는 남겨 두고 다시 시작할 때 D-52 대조부터
- **DB 구조(1700) 자체**: 적용은 한 묶음이라 오류 나면 아무것도 안 바뀜. 적용 직전 백업 CSV(구글 드라이브 'LMS 백업'). 지금 학생 0명이라 되돌릴 데이터 없음

## 7. 평가 (카톡 취소 요청 1건당)
- **LMS(지금 화면)**: 대시보드 [수업 변경] → 학생 이름 몇 글자 입력 → 학생 → 수업 → [변경] → 학생 안내 [복사] → (카톡 보내기) → [보냈어요] → 강사 안내 [복사] → (WhatsApp 보내기) → [보냈어요] = **누르기 8번 + 입력 1번** (강사 사유면 +1, 나중에 처리하면 요청 시각 고치기 +2)
- 직접 확인할 정보: 어느 수업인지(목록에서 고름)만. 6시간·변경권 잔여·적립금·보강 기한·원래 날짜는 화면이 계산해 안내문에 넣음
- **병행 기간에는 여기에 시트 기록이 더해짐** → 전환 전까지는 순수 절감 없음. 시범의 목적은 '판정·안내가 틀리지 않는지' 확인
- 기록할 것(시범 중 건마다): 누른 횟수, 시트와 다른 점, 안내 문구 고친 곳

## 8. 기준 대조
- ① 취소·변경·보강: 시범 학생은 날짜 옮겨 적기·한쪽 안내 누락(실수 ②③)이 구조적으로 막힘. 업무량 절감은 전환 뒤
- ② Class Record·수강현황 반복 확인: 병행 중엔 없음(오히려 대조 1번 늘어남). 변경권·보강 대조는 전환 뒤 사라짐. Class Record 대조는 3순위 전까지 그대로
- ③ 불필요 개발: 새 개발 없음(강사 등록은 SQL 1번). 강사 등록 화면·휴무 화면은 만들지 않고 2순위에서

## 9. 대표 결정 필요
1. **시범 학생 몇 명, 누구** (Claude 의견: 취소가 잦고, 강사가 1명이고, 미완료 보강이 단순한 학생부터. 인원은 대표가)
2. **3절 가/나** — 같은 강사의 다른 학생 시간표도 넣을지 (Claude 의견: 가. 보강 겹침을 사람이 확인하는 게 사고 ②와 같은 종류의 실수라서. 단 그 강사 학생 수가 많으면 입력 시간이 늘어나니 학생 수 보고 판단)
3. **시범 기간·전환 판단 조건** (예: 처리 ○건 동안 시트와 다른 점 0건이면 전환 — 건수·기간은 대표가)
4. **강사 Class Record의 취소 상태는 지금 누가 적는지** (강사 / 대표) — 5절 위험 막는 방법이 달라짐
5. **전환 범위**: 가. 변경권·보강만 LMS(Class Record·남은 횟수는 3순위까지 시트) / 나. 3순위(강사 Class Record)까지 전환 안 하고 병행만. Claude 의견: 가. 나는 병행 기간이 3순위 끝까지 길어져 이중 기록이 계속됨
6. 운영 조직 Pro 전환(A40)은 'LMS에만 기록 시작하는 날' — 5번이 '가'면 첫 학생 전환일이 그날인지
